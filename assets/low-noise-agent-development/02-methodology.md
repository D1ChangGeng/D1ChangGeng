## 摘要

高质量的 AI 开发协作，依赖需求、理解、实现和验证之间的准确映射。语言的作用，是让参与者共享目标、事实、责任和判断标准。

本篇提出一套工作方法：**先表达可观察的目标，校准产品心智与工程概念，再从真实材料建立系统模型，通过反例和证据校验，最后压缩为最小充分的工程约束。**已经确认的背景进入共同基线；每轮指令主要携带变化和验收差异。

这是基于工程推理整理的方法框架，用于实践和检验。文中的阶段、表格和评估指标是本系列的组织方案，并非已被实验验证的普适最优算法。它可以减少某些理解和协作成本；最终质量仍取决于实现能力、业务规则、工具权限、环境和验证。

## 一、准确界定“描述噪声”

这里把描述噪声定义为：**增加无关猜测、错误约束、概念漂移或返工风险，却没有帮助实现目标的信息和交互方式。**

噪声可以来自用户、工程师、模型、文档、工具返回和交付流程。用户采用产品语言是正常输入。负责实现的一方有责任把它翻译为可执行模型，并主动暴露重要歧义。

“用户不知道技术名词”不构成失败原因。真正需要检查的是：系统是否把体验目标误当成实现结构，是否将一个假设写进代码，是否缺少足以发现偏差的反馈。

### 1.1 优化的是总交付成本

一个有用的思考框架是：

```text
总交付成本
  = 描述与阅读成本
  + 取证与澄清成本
  + 实现成本
  + 验证成本
  + 返工与维护成本
```

这不是可直接计算的精确公式，而是比较方案时的检查框架。把提示缩短十行，若引入三轮返工，总成本可能更高。提前解释一个会改变权限或数据模型的条件，即使增加文字，也可能更经济。

因此目标是“最小充分”，即在当前共同理解和风险范围内，保留足以减少关键误判的信息。**简短是理解形成之后的结果。**

### 1.2 四种情况要分别处理

| 情况 | 本质 | 合适动作 |
| --- | --- | --- |
| 目标尚未确定 | 产品决策仍开放 | 用场景和取舍帮助决定 |
| 目标明确、术语含混 | 语义映射存在歧义 | 解释对象与责任对应关系 |
| 目标与理解明确、实现有误 | 工程缺陷 | 沿真实证据定位和修复 |
| 正确实现后目标发生变化 | 正常需求演进 | 记录变更和兼容影响 |

区分这些情况，可以避免把所有问题都归为“提示词没写好”，也避免用重复解释掩盖实现缺陷。

## 二、从产品心智进入工程模型

### 2.1 产品语言表达的是体验组织方式

用户说“让 Loop 管理整个对话”，其中的 Loop（循环）可能指一段连续工作体验；工程中的 Agent Loop（模型与工具执行循环）则可能只管理单轮执行。

正确的转换应保留产品意图：对话连续、控制一致、历史可恢复。然后说明分别由会话对象、任务生命周期、执行循环、事实记录和界面共同实现。

```text
用户的体验整体
  → 希望保持的行为和结果
  → 业务对象及其关系
  → 负责产生这些结果的工程模块
  → 实际用户路径验证
```

最后一步非常重要。工程结构再清晰，也需要重新回到用户路径，证明它实现了原始体验。

### 2.2 对一句需求分出三个成分

以“把整个对话放进 Loop，这样关闭后还能继续”为例：

| 成分 | 内容 | 处理方式 |
| --- | --- | --- |
| 目标 | 关闭后仍能继续工作 | 保留并具体化 |
| 现象/预期 | 用户重新进入同一段对话 | 转为可观察场景 |
| 实现假设 | 必须由 Loop 保存一切 | 与真实架构比较后判断 |

AI 应能够回答：“关闭”指窗口、应用、后台还是电脑？“继续”指看历史、接管运行中任务还是重启后恢复执行？这些差异会改变部署与持久化设计，值得澄清。

与此相反，函数名或目录名通常属于可由实现者自行决定的低风险选择，不必逐项要求用户批准。

### 2.3 一种有效的解释单元

陌生术语出现时，用以下四项建立理解：

```text
这个词在当前系统里指什么
它负责哪一个可观察结果
它与相邻概念如何区分
它会改变哪项开发判断
```

例如 Projection（展示投影）可以解释为：“把真实执行记录按界面规则组织成展示数据；它决定工具放在哪个折叠组，而工具是否实际成功由执行记录确定；展示位置错误时应检查这一转换。”

这种解释同时提供概念、因果关系和应用位置。代码语法仅在它会影响判断时补充。

## 三、怎样进入一个完全陌生的领域

### 3.1 从最小完整场景开始

选择一个有起点和可观察终点的行为，例如“付款后获得 API 使用额度”。先明确用户、资源、操作、成功表现以及一个重要失败情况。

先画一条候选链路，再用代码、协议和运行结果校核。系统未开发时，这是一份设计假设；系统已存在时，需要映射实际路由、函数、数据结构和存储记录。

### 3.2 正向还原与逆向溯源

正向追踪问：“接下来由谁完成什么，产出什么？”逆向追踪问：“最终显示和执行的结果凭什么成立？”

```text
正向：登录 → 创建订单 → 支付核验 → 权益授予 → API 准入
逆向：允许调用 ← 有效权益与配额 ← 正确主体 ← 已确认授予依据
```

权益可以来自购买、试用或管理授权，因此逆向检查应追踪真实依据，而不是套用“任何权益都必须有付款”的固定流程。

### 3.3 通过独立变化发现对象

若“付款成功但权益尚未发放”可以成立，支付和权益就需要能够分别表达。若“模型调用已结束但工具仍在执行”可以成立，模型调用与工具执行就有不同生命周期。

这种反例提供分层线索，但并不意味着必须建两个数据库、两个服务。**概念可分，部署可合。**

### 3.4 使用外部知识，但保持证据等级

| 材料 | 适合回答什么 | 限制 |
| --- | --- | --- |
| 当前源码与配置 | 现有实现怎样组织 | 仍需确认实际部署版本 |
| 接口与运行记录 | 这次请求实际经过哪里 | 覆盖范围可能有限 |
| 官方协议和文档 | 外部系统承诺什么 | 需匹配版本及接入方式 |
| 示例与参考架构 | 可以怎样设计 | 不能直接当作当前实现事实 |
| 团队推断 | 下一步检查什么 | 明确待验证条件 |

获得一张“看起来专业”的架构图，只完成了候选建模。可用于开发的模型还要标注来源、版本、假设和未知点。

## 四、怎样生成足够有用的分层视图

### 4.1 分层依据是变化和责任

沿链路寻找四类分界：

| 分界 | 检查问题 |
| --- | --- |
| 职责变化 | 这里开始解决另一类问题了吗？ |
| 数据变化 | 输入输出的结构或含义改变了吗？ |
| 权威变化 | 谁有资格决定这个事实成立？ |
| 执行变化 | 是否跨进程、网络、权限或生命周期？ |

例如 `Event → Projection → ViewModel → Component` 是事件、转换、输出数据与界面呈现之间的关系。图中的箭头不能自动理解为网络调用，方框也不能自动理解为独立模块。

C4（多层次软件结构建模方法）及其动态视图是可借鉴的图示工具。工具帮助表达关系，关系本身仍应来自当前问题。[R28](05-references.md#r28) [R29](05-references.md#r29)

### 4.2 按问题选择视图

| 当前问题 | 最有价值的视图 |
| --- | --- |
| 功能该放在哪里 | 职责与依赖 |
| 先后顺序异常 | 执行时序与因果关联 |
| 某字段丢失或重复 | 数据转换与身份映射 |
| 停止、恢复、退款行为异常 | 状态机与合法转换 |
| 跨端控制或后台存活 | 部署与生命周期 |
| 越权或敏感数据外发 | 信任、权限与数据流向 |

小型样式修改可以只检查组件和视觉证据；涉及任务恢复时才展开状态、持久化和外部副作用。分析的规模随决策风险增长。

### 4.3 每个箭头需要什么信息

最小连接说明包括：传递什么、怎样关联对象、接收方作出什么判断、产生什么结果、失败时如何观察。

例如“工具结果进入下一次模型调用”需要保留调用标识、结果内容及提供方要求的上下文结构。“事件进入投影”需要明确顺序、去重、删除/修订语义和展示规则版本。

只有节点名称而没有连接契约的模型，很难支持可靠实现。连接约定不清楚时，增加更多节点通常不能消除歧义。

## 五、形成可操作的八步协作循环

这八步是一套工作顺序，可以合并执行。它们的产物是短而可复用的共同基线，而非每次都生成完整文档。

### 第一步：固定目标和观察范围

给出一个用户行为、一个预期结果、一个真实示例。明确保留什么体验、当前覆盖哪些平台，以及成功需要观察到什么。

产物可以只有一句话：“工具执行中的输出与执行后的完整结果，都显示在同一个可展开单元中；重新打开历史后仍可查看。”

### 第二步：分离事实、意图和假设

现象作为观察，目标作为要求，根因和实现方式作为待验证假设。对会改变范围的歧义优先澄清；可安全逆转的局部选择允许实现者提出默认方案。

### 第三步：校准关键概念

仅解释会改变实现的概念。用用户体验描述、领域对象、责任模块三列完成映射。让用户确认“我想达到的效果确实被保留”，而不是让用户背诵框架术语。

### 第四步：还原当前实现

读取相关代码、配置、协议和实际数据，建立最短的完整链路。区分现状、目标和差距。同一源代码在不同配置下可能表现不同，所以记录提交版本和关键环境。

### 第五步：提取必要约束

确定事实来源、身份关系、生命周期、资源边界、必须保留的行为及验证标准。把这些约束放到正确位置。

### 第六步：小步实现并形成反馈

优先完成能贯穿真实入口到结果的一段功能。检查中间证据，避免所有模块最后才首次连接。局部实现选择围绕现有工程和已确认约束推进。

### 第七步：验证目标与实现的双向一致性

从用户路径向下确认实际调用，从结果向上核对事实依据。模拟验证控制分支，真实环境验证连接和副作用，界面验证呈现。证据支持的范围就是当前可以宣称的范围。

### 第八步：更新基线并压缩下一轮指令

保留确认后的术语、决策、接口、验证结论和待决问题。新一轮只传达变化、影响范围和新增验收条件。旧的临时推断不继续作为隐含约束传播。

## 六、从多个维度降低噪声

### 6.1 语言维度：给术语提供当前语境

优先中文解释和具体结果。英文保留用于对应源码和文档。一个词在不同层次使用时加限定词，例如“业务会话”“登录会话”“数据库会话”。给代码标识定义一次稳定含义，再按需引用。

形容词转换成可观察条件：“稳定”可以拆成断线后恢复、重复事件去重、未知副作用不盲重试；“简洁”可以拆成默认展示范围、展开层级和信息密度。

### 6.2 认知维度：允许从低技术知识入口开始

用户只需提供任务、示例和偏好；AI 承担初步概念映射、实现调查和关键问题提取。技术解释的深度以“用户能作出当前必要决定”为准。

衡量是否理解，可以让用户预测：“窗口关闭后后台是否继续？”“审批通过但操作系统拒绝写入时显示什么？”能预测关键行为，比能够复述名词更有价值。

### 6.3 架构维度：约束正确性，保留局部实现空间

优先规定用户体验、权威事实、接口语义和资源边界。具体状态库、函数拆分和样式实现由实际代码条件决定。

明确约束也需要范围。比如“保持组件不变”应说明保留的是视觉语法、公共属性、组件身份还是全部内部实现。绝对化表述若没有范围，可能阻止必要修复。

### 6.4 上下文维度：维护可引用的项目基线

建议保存少量可定位资料：目标、术语与决策、接口约定、当前实现映射、验证记录。每项具有版本或更新日期，关键结论带来源。

权威性按问题区分：需求文档说明目标，源码说明实现，运行记录说明该次实际行为，官方协议约束外部接口。它们冲突时应显式解决，不能以“最新文件总是正确”机械覆盖。

### 6.5 决策维度：让澄清与自主推进有边界

涉及产品范围、资金、数据删除、权限提升或公开发布时，执行者应依据明确授权；必要的缺失决定需要确认。已有约束内、可逆的小改动可以自主实施并验证。

有效澄清提供“哪个决定影响什么”，例如：“退出整个应用后是否继续执行？这决定后台是否要独立常驻。”避免让用户在不了解后果时选择技术名称。

### 6.6 实现维度：先查证，再选择最小改动

要求沿真实链路取证，识别最先可观察到偏差的边界，再提出修复。首次偏差未必是最终根因，但比按界面现象直接猜文件更有定位价值。

保留能够重现问题的最小样本，并让修复前后的差异可检查。对现成框架，先明确已有能力、配置问题和真实缺口，再决定扩展。

### 6.7 验证维度：证据与承诺同尺度

“测试通过”应能回答：哪个版本、什么环境、覆盖什么路径、哪些依赖被模拟。视觉截图不能单独证明权限或持久化；模拟支付不能证明生产支付已开通；服务端日志不能单独证明客户端已经收到事件。

将证据关联到需求，而不是堆积文件数量。验证不足时，交付结论保留明确边界。

### 6.8 交付维度：使用当前成立的结果组织文本

标题、说明、提交信息和交接文档描述已确认的能力、范围和证据。需要审计的变更、兼容性和安全限制如实保留。no-negative-echo（以最终成立的结果组织交付文本的写作规则）为这种成文方式提供了明确参考。[R30](05-references.md#r30)

编辑上的正向表达服务于理解效率；实际失败、遗留风险和未验证范围仍是读者需要的事实。

## 七、怎样确定学习与分析已经足够

陌生领域可以无限深入。为了支持当前开发，采用以下“足够理解”标准：

| 能力 | 可检验表现 |
| --- | --- |
| 还原 | 能解释入口到结果经过哪些关键责任 |
| 区分 | 能说明体验整体、领域实体和实现模块的差异 |
| 预测 | 能预测一个变更影响哪些边界 |
| 诊断 | 能提出可以由证据支持或推翻的假设 |
| 验收 | 能判断哪类证据足以支持当前承诺 |

当主要不确定性已经转化为可执行验证，继续扩展名词和架构图的边际价值会下降。这时应进入小步实现。

反过来，如果仍无法说明权益授予给谁、回退是否修改文件、停止是否取消后台执行，就属于会改变产品行为的关键未知，需要继续对齐。

## 八、把复杂理解压缩成最小充分的工程描述

### 8.1 五个必要成分

```text
目标行为
+ 当前可信基线
+ 必须保持的约束
+ 本轮变更范围
+ 验收证据
```

这些成分可以压缩为一段话，也可以在复杂任务中分别展开。共同基线成熟时，引用版本比重新解释全部背景更有效。

### 8.2 三种阶段使用不同语气

**调查阶段：**“围绕这个执行实例核对数据链路，区分已验证事实和根因假设，指出证据支持的修复位置。”

**实施阶段：**“按已确认契约修改对应映射，保留稳定身份和现有展示规则，补充该失败路径的回归测试。”

**验收阶段：**“比较实时与历史重建结果，并提供相同调用标识对应的记录、视图数据和界面证据。”

调查时保持假设可变，实施时固定已确认约束，验收时要求证据。把三个阶段混在一条模糊命令里，容易产生反复分析或无依据修改。

### 8.3 一条短指令为何能够有效

> 保持现有展示语法，沿工具结果到视图的链路修复首次数据偏差；同一调用的请求、结果和状态保持稳定关联，并证明实时更新与历史重建一致。

这句话有效的前提是双方已知道现有展示语法、身份字段和验证环境。缺少这些共同背景时，应附一个样本和一份简短基线。压缩程度由共享理解决定，而非由固定字数决定。

## 九、把连续协作变成可累积的经验

### 9.1 每次解决问题后沉淀四项信息

保存问题的可观察表现、真正失效的边界、修复后必须保持的约束、能发现再次发生的测试。它们比完整聊天记录更容易在下次任务中复用。

例如：“历史重复工具单元”可以沉淀为“重连重复事件必须幂等消费，展示以执行身份关联；保留重复投递测试”。下次出现类似症状时先使用规则和测试，再检查具体环境。

### 9.2 以增量变更维护共同基线

需求变更记录应指出：哪项已确认决定被替换、为什么、影响哪些契约、哪些行为继续保留、怎样更新测试。旧规则可以保留于决策历史，当前执行入口只引用现行基线。

同样重要的是区分“目标变化”与“发现先前理解不足”。前者需要产品取舍，后者需要修正映射或补齐证据。

### 9.3 按决策风险选择必要流程

每轮使用与风险相称的最小流程。改一个边距可以给截图位置和预期；修改支付权益或任务恢复则需要状态和副作用分析。模板提供可选检查项，真正的管理对象是当前不确定性。

## 十、怎样检验这套方法是否提高效率

以实际交付过程和结果评价方法，可围绕同类任务记录以下指标：

| 指标 | 记录方式 | 解释限制 |
| --- | --- | --- |
| 到验收完成的时间 | 从目标确认到证据通过 | 排除等待外部权限等时间或单列 |
| 语义返工次数 | 因理解不一致而重做的次数 | 与正常需求变化分开 |
| 关键澄清成本 | 澄清次数及改变的决策 | 次数少不自动更好 |
| 首次验收通过率 | 按事先约定场景统计 | 避免事后降低标准 |
| 回归与维护成本 | 后续缺陷、重复修复 | 需要足够观察周期 |
| 用户决策负担 | 必须由用户处理的事项 | 区分必要产品决定和可委托细节 |

开展比较时，应尽量保持任务复杂度、模型、工具权限和环境相近。可以先记录基线，再对类似任务使用“场景—模型—证据—压缩”流程。样本少时结论只适用于观察到的任务。

这些指标支持根据实际交付数据持续修正方法，并明确其有效范围。

## 十一、方法的适用边界

准确描述能够减少歧义，不能替代正确代码、充分授权、可靠依赖或真实验证。某些并发问题需要深入代码，某些安全和金融业务需要专业审查，某些目标必须通过试验确认可行性。

分层模型也可能不完整。出现解释不了的反例时，应更新模型，而不是让现实迁就图。稳定基线用于减少重复解释，同时保留随证据修订的能力。

协作系统应主动识别隐藏风险、指出缺失条件、提供有根据的选项，并将高代价决定交由适当的责任人确认。

## 结语：低噪声开发是一套闭环能力

```text
观察产品行为
  → 提取意图并分离假设
  → 校准心智模型
  → 还原领域、职责和执行链路
  → 用反例与证据检验
  → 形成必要约束
  → 实施和验收
  → 更新共同基线
  → 用更短的语言推进下一轮
```

这条链路把“表达得像工程师”转化为更实际的目标：**在正确的位置约束系统，并能够解释和验证结果。**语言随共同理解而简化，速度随返工和无效决策减少而改善，质量由明确契约与真实证据支撑。
