## 使用方法

每个案例依次说明：用户体验目标、隐藏假设、概念映射、执行与数据链路、反例、证据和精炼开发描述。案例中的标识、轨迹和检查结果均为教学构造，不表示某个真实项目已经发生这些故障或完成验证。

练习时先尝试解释“最终结果凭什么成立”，再阅读诊断。目标是积累发现对象和责任边界的能力，而不是记住一组固定模块名称。

## 案例一：用户感受到的是一段连续对话

### 1. 目标与当前直觉

用户希望 Agent（智能体）持续工作：发送任务，观察执行，补充要求，停止，重新打开后继续。于是提出：“整个产品都应该围绕 Loop 管理。”

这里的 Loop（循环）可能指完整对话体验，也可能指模型与工具交替执行的循环。先提取目标：**连续上下文、统一控制、可查看历史和明确的恢复方式。**

### 2. 把同一体验映射到不同层次

| 用户感知 | 领域对象 | 工程责任 |
| --- | --- | --- |
| 同一段长期对话 | Thread（业务会话） | 组织消息、分支与相关任务 |
| 这次要求正在执行 | Turn（任务轮次） | 管理受理、运行和终止 |
| Agent 连续采取行动 | 模型调用与工具执行 | Agent Loop（执行循环）推进工作 |
| 能停止或继续 | 控制命令及状态转换 | 可信控制接口与执行所有者 |
| 重新打开仍能看到 | 已保存内容和状态 | 查询、投影与界面重建 |

这些是本系列的参考建模约定；现有框架采用不同名称时，需要映射含义。

### 3. 用三个场景检验范围

用户只查看历史时，执行循环可以没有运行；后台执行时，桌面窗口可以没有打开；两个独立任务可以各有执行循环，却出现在同一个工作界面。

由此得到：**体验的聚合边界、对象生命周期和代码执行边界可以不同。**产品仍然可以以对话为中心设计导航和控制，工程上则由不同职责共同维持这一体验。

### 4. 精炼描述与验收

> 产品以连续会话组织任务和历史，任务轮次拥有明确生命周期，执行循环推进模型与工具。控制、持久化和展示共同保证跨轮连续性；明确关闭窗口、退出应用和后台重启后的行为。

验收分别覆盖历史查看、运行中退出界面、重新接入和后台重启。只验证“发送后收到回答”，不足以证明连续体验。

## 案例二：工具执行正确，界面却缺少输出

### 1. 可观察目标

用户展开工具单元时，可以查看本次请求、运行中输出和最终结果；重新打开历史后，仍与原来的工具执行保持正确关联。

### 2. 模型与连接

```text
工具产生实际结果
  → 权威执行记录
  → 查询 / 事件传输
  → Projection（展示投影）
  → ToolUnitView（工具单元视图数据）
  → Component（界面组件）
```

这是一条数据转换链路，不要求每个节点都是独立服务。每段连接需要保留工具执行标识、结果引用和保留策略。

### 3. 假设性的诊断过程

| 检查位置 | 教学示例中的发现 |
| --- | --- |
| 实际执行 | 有输出，退出码为零 |
| 权威记录 | 同一 `invocationId` 保存了结果引用 |
| 客户端接收 | 收到了对应引用 |
| 展示投影 | 仅复制标题和状态，遗漏结果引用 |
| 组件 | 得到的数据中没有结果入口 |

此时证据指向投影边界。可以先修复映射并补充测试，再判断是否还存在组件问题。直接给组件填一条“执行成功”的兜底文本，会改变显示，但不能补回真实结果。

如果事件尚未到达、结果因权限被过滤、日志按策略截断，也可能出现类似现象。定位需要同一实例、同一版本和同一访问身份的证据。

### 4. 精炼描述与验收

> 保持现有工具单元交互，沿执行结果到视图数据核对同一次调用，修复有证据支持的数据缺口；说明截断与访问策略，并验证运行中更新、完成后展开和历史重建。

补充一个投影测试和一个真实界面场景。组件本地状态是否在重组后保留，还要检查 React（界面组件库）的类型、位置与键，而不只检查业务标识。[R11](05-references.md#r11)

## 案例三：进入陌生的认证与支付领域

### 1. 用户看到的是连续购买体验

```text
注册登录 → 选择套餐 → 完成支付 → 获得额度 → 调用 API
```

API（应用程序接口）是产品对程序调用者开放的能力。上面的体验很简洁，实际需要回答几种不同问题：是谁、买了什么、交易是否符合生效条件、权益授予谁、这次请求能否执行。

### 2. 首先澄清“认证”

Authentication（身份认证）确认访问主体；Authorization（权限判定）确定可执行的操作。实名认证、支付通知验签和接口密钥验证又有各自的目标，讨论时应点明范围。

OIDC（OpenID Connect，开放身份认证协议）在 OAuth 2.0（授权框架）上定义身份认证能力。[R25](05-references.md#r25) 已登录访问者对具体订单和组织仍需资源级授权检查。[R20](05-references.md#r20)

### 3. 从可以独立变化的事实发现对象

| 对象 | 记录的业务事实 | 一个检验范围的反例 |
| --- | --- | --- |
| 用户与登录会话 | 访问身份及登录状态 | 用户退出，购买的服务仍有效 |
| 组织与成员关系 | 谁属于哪个使用主体 | 付款管理员与实际使用成员不同 |
| 商品、套餐和价格 | 售卖什么、交易条件是什么 | 当前价格变了，旧订单仍保留原条件 |
| 订单 | 一次购买的内容和应付条件 | 已创建订单，尚未付款 |
| 支付交易 | 外部支付过程及已核验结果 | 支付成功，权益发放尚未完成 |
| 产品权益 | 某主体有权使用哪些能力 | 免费试用也可以授予权益 |
| API Key（接口访问密钥） | 哪个主体持有什么访问凭据 | 凭据有效，但作用范围不足 |
| 配额与用量 | 可使用多少、实际消耗多少 | 套餐有效，但额度已经耗尽 |

采用周期订阅时，再引入 Subscription（订阅关系）及续期、取消、宽限等规则；采用充值额度时，其生命周期则不同。领域对象要由商业模式推出。

### 4. 三条实际链路

**登录与业务身份：**

```text
登录交互
  → 身份服务确认身份
  → 建立本地用户 / 组织关联
  → 创建或验证登录会话
  → 业务接口解析可信主体
  → 检查该主体对目标资源的权限
```

外部登录身份、本地用户和组织需要稳定映射。邮件地址等展示属性能否作为关联依据，需要明确验证与账号合并规则。

**购买与权益：**

```text
客户端提交套餐选择
  → 服务端确认购买主体、价格和币种
  → 保存订单及价格快照
  → 创建外部支付流程并保存关联标识
  → 接收并验证支付结果，必要时主动查询
  → 更新交易与订单事实
  → 按规则幂等发放权益
  → 账户接口返回当前权益
```

Webhook（服务端事件通知）是一种常见支付结果入口。以 Stripe Checkout 为例，官方要求可靠履约不能只依赖用户返回成功页面，并要求处理同一会话的重复或并发履约；延迟付款方式也需要依据真正的支付状态处理。[R26](05-references.md#r26)

回调签名验证、事件类型、交易关联、金额币种和商户环境应按采用平台核验。Stripe 还明确要求处理重复事件，且不保证事件按生成顺序投递。[R27](05-references.md#r27) 其他平台的签名字段、应答格式和重试契约应独立核查。

**实际 API 准入：**

```text
验证访问密钥
  → 解析用户 / 组织 / 应用主体
  → 检查凭据范围和资源授权
  → 检查有效权益
  → 检查速率与额度，按设计预留资源
  → 执行业务请求
  → 按实际结果记录和结算用量
```

Rate Limit（速率限制）约束一定时间内的调用频率；Quota（配额）约束可使用总量。并发请求需要明确原子扣减、预留和结算方式。失败退款、超时结果未知、超额使用和后付费是否允许，都属于产品策略。

### 5. 用户未看到的中间状态

```text
支付：已核验成功
订单：已付款
权益：等待发放
账户页面：付款已确认，服务开通处理中
```

这是可以显式管理的中间状态。发放失败时保留重试或人工处理入口，账户页面展示对应事实。对账可以发现支付记录与本地状态之间的差异。

退款记录应与原交易关联。部分退款是否减少权益、订阅取消何时生效、已消耗额度如何处理，需要产品定义。支付“成功”也要注明依据的是哪种支付方法及业务阶段，避免把付款确认、资金结算和后续争议处理压缩成一个无条件永久状态。

### 6. 一次教学诊断：已付款却无法使用

假设逐层检查发现：支付已确认；订单属于 `org_A`；权益正确授予 `org_A`；本次密钥却属于 `org_B`。

此时根因线索是调用主体与权益归属不一致。修改成功页面或重复发放权益都不是有根据的修复。应检查组织选择、密钥创建上下文和资源授权映射。

另一个反例是通知重复：同一笔交易到达两次，如果权益延长两次，就需要检查业务幂等约束。消息去重和权益授予去重可以协同，但只记住某个通知 ID，未必覆盖不同事件表达同一业务效果的情况。

### 7. 可交给工程师的描述

> 以明确的购买主体建立订单，服务端确定交易条件，并依据平台核验结果更新支付事实；按订单与权益规则执行幂等发放。API 准入统一检查主体、凭据范围、权益和配额。覆盖重复与乱序通知、发放失败、用户未返回页面、组织切换和并发额度请求，提供交易、权益及实际调用证据。

这段描述有效的前提，是套餐类型、权益主体和生效/撤销规则已经确认。缺失这些商业决定时，先给出影响说明和候选规则，再推进实现。

## 案例四：关闭后继续，与回到过去，分别意味着什么

### 1. 把“恢复”转换成场景

| 用户说法 | 可能需要的能力 |
| --- | --- |
| 再次打开能看到之前内容 | 历史查询与界面重建 |
| 网络恢复后接着看 | 重新连接、补齐事件 |
| 后台崩溃后接着做 | 执行检查点、外部结果核对 |
| 回到之前一条消息重新提问 | 历史分支与上下文选择 |
| 回到修改文件之前 | 工作区快照与回滚 |

不同目标可以组合，但应分别承诺和验证。

### 2. 副作用后的崩溃

```text
记录工具待执行
  → 修改文件成功
  → 在提交结果前崩溃
  → 重启时只有“运行中”记录
```

恢复逻辑需要检查文件、版本或操作标识，确认已发生效果，再决定补记结果、重试或要求介入。数据库事务只覆盖其管理的修改；外部操作的协调需要额外设计。[R16](05-references.md#r16)

幂等键是否有用，取决于执行边界是否真正识别并约束重复请求。[R19](05-references.md#r19) 记录“最后一次调用未完成”，只能说明系统缺少完成证据，不能推导外部操作未发生。

### 3. 停止与恢复的时序

```text
用户请求停止 → 状态变为停止中
工具可能已经完成部分效果
执行者完成取消和收尾 → 提交终态及已有结果
```

停止请求与正常完成可能竞争。后端按明确状态规则决定最终结果；迟到的工具事实应如实关联，不应为了维持一个预期界面而抹掉已发生效果。

Resume（继续执行）是否允许作用于已停止任务，需要定义：恢复原执行、创建新尝试，或创建新的任务轮次。暂停和终止采用不同语义时，在接口及界面中明确区分。

### 4. 回退与取消回退

历史消息编辑可以产生新分支；进入回退预览可以暂时切换显示和草稿。取消预览、切回旧分支、撤销文件变化是不同操作。若新分支已经执行并修改工作区，“取消回退”需要额外说明是否恢复文件及如何处理冲突。

### 5. 精炼描述与验收

> 分别定义历史重建、执行继续和工作区回滚；以稳定分支和执行身份追踪状态。未知工具结果先核对，停止与完成竞争按状态机处理；覆盖副作用后崩溃、重新进入历史、切换分支及取消预览。

## 案例五：批准操作之后，执行权到底在哪里

### 1. 产品目标

用户希望低风险操作自动完成，重要操作经过确认，Agent 始终在已授权范围内工作。

### 2. 五类事实

| 层次 | 具体事实 |
| --- | --- |
| 用户目标 | 修复指定工作区 |
| 模型意图 | 请求运行某条命令 |
| 策略判断 | 该主体在此环境是否允许这样操作 |
| 审批许可 | 允许哪次请求、什么资源和有效范围 |
| 实际效果 | 程序真正访问和修改了什么 |

用户批准是授权过程中的一个事实。执行器仍需确认请求未被替换、许可仍有效、用户有权授予该范围，并由实际环境落实访问限制。[R20](05-references.md#r20) [R22](05-references.md#r22)

### 3. 用反例检查安全心智

“只读”可能读取密钥并把内容发往模型服务；“运行测试”可能执行项目自定义脚本；“独立进程”可能仍拥有当前用户的全部文件权限。npm 的脚本机制支持项目定义执行内容，因此命令名称不足以描述全部效果。[R23](05-references.md#r23)

Prompt Injection（提示词注入）还可能让外部文件或网页中的文字影响模型后续行动。模型指令、数据来源和系统授权需要分层防护。[R21](05-references.md#r21)

### 4. 一次教学诊断

批准内容限定工作区写入，但发现外部文件变化。沿链路检查：模型请求、真实路径解析、策略结果、批准范围、执行入口、操作系统限制和最终文件变化。

若某个工具绕过统一执行入口，修复权限执行路径；若策略正确但隔离未启用，修复实际运行配置。提示词调整可以辅助模型行为，却不能替代不可绕过的执行约束。

### 5. 精炼描述与验收

> 模型调用意图经可信策略和必要审批后，由统一执行边界落实。许可绑定具体请求、资源和环境；限制文件、网络与凭据访问，记录实际结果。验证拒绝操作没有产生对应副作用、请求变化使旧许可失效、隔离机制失效时按规则处理。

## 案例六：面对文件解析，怎样自己生成模型

### 1. 初始需求

“上传文件后显示解析结果。”先固定一个小场景：单用户上传一份支持格式的文件，得到可定位到原文的解析内容；解析失败时有明确状态和原因。

### 2. 建立候选链路

```text
文件选择
  → 上传和输入校验
  → 原始文件保存
  → 解析任务建立
  → 解析器读取特定文件版本
  → 结果保存并关联来源
  → 查询结果
  → 展示内容与原文位置
```

这是候选设计。小文件同步解析、直接对象存储上传或第三方解析服务都可能改变具体实现。先确认现有系统和规模要求，再选择路径。

### 3. 从结果反推隐藏需求

页面凭什么知道内容来自哪份文件？需要稳定的文件身份、版本或内容校验。多次解析后使用哪个结果？需要解析版本或当前选择规则。文件成功上传但解析失败？需要独立的任务状态。解析器升级后结果变化？需要记录处理配置及版本。

如果输出需要标明原文页码，就应保存来源定位关系。只保存一段文本，之后可能无法可靠还原它来自哪个位置。

### 4. 最小契约

| 边界 | 输入 | 输出 | 关键约束 |
| --- | --- | --- | --- |
| 上传 | 文件及访问主体 | 文件标识和版本 | 格式、大小、访问范围 |
| 解析 | 指定文件版本及配置 | 解析结果及来源定位 | 结果对应同一输入版本 |
| 保存 | 结构化结果及任务身份 | 可查询的结果引用 | 状态与结果可关联 |
| 展示 | 查询结果及权限 | 页面内容 | 标注来源、失败和保留策略 |

### 5. 精炼描述与验收

> 上传、解析与展示保留稳定的文件版本和任务关联，结果能够追溯原文位置；明确上传成功、解析中、解析失败和完成的不同状态。使用固定样本核对结果、来源定位和重新加载行为，再验证真实上传链路。

## 跨案例总结：可迁移的是识别方法

| 反复出现的问题 | Agent | 认证支付 | 文件解析 |
| --- | --- | --- | --- |
| 体验整体对应多个对象 | 对话与执行循环 | 购买与交易、权益 | 上传与解析任务 |
| 事实由谁确认 | 执行记录 | 核验交易和权益规则 | 输入版本和解析结果 |
| 生命周期分别变化 | 调用完成但任务继续 | 已付款但开通处理中 | 已上传但解析失败 |
| 外部结果可能先发生 | 文件已改，记录未写 | 交易成功，本地未同步 | 文件已存，任务未建立 |
| 界面依据派生数据 | 执行投影 | 账户权益查询 | 解析结果展示 |

进入新领域时，依次询问：**哪些条件可以独立变化；谁有权确认事实；每一步需要什么输入；失败后怎样知道实际发生了什么；最终体验如何验收。**答案逐渐构成模型，模型再压缩为开发描述。
