## 阅读目标：掌握会改变开发判断的知识

使用 AI 开发 Agent（智能体）产品时，最值得优先学习的知识，是能够改变需求表达、模块归属、方案选择和验收判断的知识。

例如，“让停止按钮正常工作”可以进一步表达为：“停止是后端执行控制命令；界面先显示正在停止，执行系统确认模型请求和工具执行的实际终态后，再显示已停止。”这段表达能够约束真实实现，同时把具体函数和界面库的选择留给工程师。

本篇覆盖六组工程知识：应用宿主、进程通信、界面投影、执行引擎、可靠性、安全。每组知识都围绕三个问题展开：**用户看到什么；系统怎样产生这个结果；开发时应约束什么。**

### 本文的语义约定

本文将 Harness 称为“Agent 执行控制系统”，将 Runtime 称为“执行引擎”。这些名称在不同项目中边界可能不同。下文的 Thread（业务会话）、Turn（任务轮次）、ModelStep（模型调用步骤）是本系列采用的一组明确约定，接入现有框架时需要建立对应关系。

特别约定：一个可观测的模型调用实例对应一个 ModelStep；工具执行具有独立身份和生命周期。框架若把多次重试包装成一次逻辑调用，应额外记录 Attempt（实际尝试）及其关联，按可观测程度如实说明。这里的划分是产品建模选择，适用性由工程契约决定。

## 一、先建立四张互补的工程地图

架构首先说明系统由哪些部分构成、谁负责什么、怎样合作、怎样维持正确性。阅读架构图时，先判断它描绘的是哪种关系。

| 视图 | 回答的问题 | Agent 产品示例 |
| --- | --- | --- |
| 产品体验 | 用户怎样完成一件事 | 输入任务、观察执行、停止、重新进入历史 |
| 业务领域 | 系统管理什么对象和规则 | 会话、任务轮次、模型调用、工具执行 |
| 模块职责 | 哪一组代码承担哪项责任 | 控制接口、执行引擎、工具系统、展示投影 |
| 运行部署 | 代码在哪里运行和通信 | 桌面渲染进程、本地后台、远程服务 |

数据流、状态机和信任边界可以作为这些视图的补充。C4（以不同抽象层次表达软件结构的建模方法）提供了结构视图及动态视图的公开参考；实际任务按需要选用即可。[R28](05-references.md#r28) [R29](05-references.md#r29)

一个独立模块可以与其他模块运行在同一个进程中。同一份共享代码也可以被两个进程分别加载，形成彼此独立的运行实例。因此，**代码复用、运行实例共享、数据共享，是三个分别需要确认的决定。**

## 二、应用宿主：桌面端与命令行端怎样组成

### 2.1 桌面应用中的职责

Electron（桌面应用框架）提供窗口、进程和系统集成能力；React（界面组件库）描述窗口内部的界面。Electron 的 Main Process（主进程）负责应用与窗口管理，Renderer Process（渲染进程）承载网页界面，Preload（预加载脚本）在渲染进程中的相应上下文执行并建立受限能力桥梁。[R01](05-references.md#r01)

一个适合讨论的部署方案是：

```text
桌面应用
├─ 主进程：窗口、应用生命周期、受控系统接口
├─ 渲染进程
│  ├─ 预加载脚本：向界面暴露限定接口
│  └─ React 界面：输入、消息、工作区、交互状态
└─ Agent 执行宿主：按需要采用独立后台进程
   ├─ 执行控制系统
   └─ 工具执行器 → 外部工具进程
```

Agent Host（执行宿主）表示承载执行引擎的运行角色，可以采用独立子进程，也可以连接一个已有服务。独立进程有利于划分故障和生命周期边界；实际权限隔离需要另外设计。

桌面界面应通过限定接口访问高权限能力。Electron 官方建议启用上下文隔离、限制网页权限、校验进程通信的发送方，并避免把任意通信能力直接暴露给页面。[R02](05-references.md#r02)

**可直接使用的要求：**桌面界面负责交互，可信后台负责工具执行和权限；明确窗口关闭、应用退出、后台异常时任务分别如何处理。

### 2.2 命令行与终端界面

CLI（命令行接口）让用户用命令和参数操作程序；TUI（终端交互界面）在终端中持续显示输入框、消息和进度。二者可以属于同一个产品的不同运行模式。

在一种 TypeScript（带类型约束的 JavaScript 开发语言）方案中，Node.js（程序运行环境）执行代码，Commander.js（命令参数解析库）解析命令，Ink（基于 React 的终端界面库）负责交互显示。[R08](05-references.md#r08) [R09](05-references.md#r09)

```text
agent                         → 进入交互界面
agent run "检查项目"          → 执行一次任务，输出文本
agent run "检查项目" --jsonl  → 按行输出结构化数据
```

这些命令是示例产品接口。非交互模式可以完全不启动终端界面。

程序的 stdin（标准输入）、stdout（标准输出）和 stderr（标准错误/诊断输出）可能连接终端，也可能连接文件或其他程序。Node.js 提供 TTY（终端连接）检测能力。[R07](05-references.md#r07)

因此建议明确输出契约：机器模式的标准输出只包含约定数据，诊断输出单独处理；退出码反映命令结果；取消、管道中断和无交互环境有确定行为。拥有漂亮的终端界面，只证明其中一种使用方式成立。

### 2.3 共享代码与共享任务

| 产品目标 | 对运行架构的要求 |
| --- | --- |
| 桌面端与命令行分别使用相同能力 | 可复用执行核心，各自运行实例 |
| 两端查看和控制同一个运行中的任务 | 连接共同执行所有者，或采用明确的协调机制 |
| 关闭桌面窗口后继续执行 | 后台生命周期覆盖窗口生命周期 |
| 整台电脑关机后继续执行 | 执行环境独立于这台电脑 |
| 远程运行但修改本地文件 | 增加经过授权的本地执行边界 |

Local Daemon（本地常驻后台服务）是一种共享任务的实现方案。Remote Runtime（远程执行引擎）则把任务放在服务器。模型服务、执行引擎、工具和文件可以位于不同环境；需要分别标明位置和授权关系。

**工程判断：**先确认任务由谁拥有、文件在哪里、关闭什么之后任务仍应存活，再决定进程和服务数量。

## 三、异步与通信：等待任务时系统怎样保持可操作

### 3.1 只需要掌握的运行机制

Process（进程）是运行中的程序实例；操作系统 Thread（线程）是执行单元；业务 Thread（会话）则是产品数据对象。同名术语应标明所属层次。

`async/await` 是异步编程语法，Promise 是未来结果的表示。等待异步网络响应时，当前函数可以暂停后续步骤，让运行环境处理其他工作；持续进行同步计算则会占用执行线程。Node.js 的 Event Loop（事件循环）负责调度可执行工作，工作线程可用于计算密集型 JavaScript 任务。[R04](05-references.md#r04) [R05](05-references.md#r05)

这解释了一个产品要求：“等待模型期间仍能处理停止”。实现需要让控制请求有机会被处理，并将取消意图传播给实际执行者。仅给函数加上 `async`，并未说明耗时部分采用了何种执行机制。

运行编译器或测试程序时，Node.js 可使用 `child_process`（子进程模块）启动外部进程并读取输出。实际工程还需处理启动失败、退出码、输出上限、取消和进程树清理。[R06](05-references.md#r06)

### 3.2 通信机制与业务契约

同进程组件可以函数调用，跨进程组件需要通信。IPC（进程间通信）是总称，Electron 内置通信是其中一种具体机制。HTTP（网络请求协议）也可以用于本机服务。SSE（服务器发送事件）承载服务端持续发送的数据；WebSocket（双向持续通信协议）适合需要双向消息的连接。

Electron 的请求/响应及主动推送模式有官方接口。[R03](05-references.md#r03) SSE 的事件标识和重连机制由协议定义，但历史保存、游标过期、权限过滤和业务补齐需要应用提供。[R15](05-references.md#r15)

**接口说明做什么，传输说明怎样到达。**同一个 `stopTurn` 可以经桌面进程通信、本地调用或网络请求实现，停止的业务含义应保持一致。

### 3.3 命令、回执、事件、快照

| 数据 | 含义 | 示例 |
| --- | --- | --- |
| Command（命令） | 请求系统采取行动 | 停止某个任务轮次 |
| Receipt（回执） | 命令被受理或拒绝的结果 | 已受理，并返回任务标识 |
| Event（事件） | 已发生的变化或明确标记的进度 | 工具已启动、任务已停止 |
| Snapshot（状态快照） | 某个记录位置上的状态 | 会话当前任务、内容和游标 |

先返回回执再推送事件，是一种实现方式。同步接口也可以等待任务终态后返回。业务上的“同步等待最终结果”与阻塞程序线程是不同概念；连接超时、调用方等待时限、任务预算和取消策略也应分别定义。

**可直接使用的要求：**明确提交回执、进度事件和最终结果的语义，说明断线是否影响任务执行，并提供可查询的任务标识。

## 四、界面架构：事实怎样形成用户看见的内容

### 4.1 数据转换链路

```text
权威执行事实
  → 事件 / 状态快照
  → Projection（展示投影：按规则组织数据）
  → ViewModel（视图模型：供界面使用的数据结构）
  → Component（组件：实际显示和交互）
```

这是数据变换视图。事件和视图模型是数据，投影是变换过程，组件是呈现单元；它们可以由少量模块完成，无需分别部署成服务。

例如，一次工具执行保存调用身份、输入、状态和结果。展示投影生成工具单元，组件显示标题、状态及可展开的请求与结果。用户只看到一个单元，底层则有明确的事实来源。

### 4.2 三种状态分别归谁

| 状态 | 例子 | 维护位置 |
| --- | --- | --- |
| 权威业务状态 | 工具是否完成、任务是否停止 | 执行控制系统和可信存储 |
| 客户端数据状态 | 已加载的数据、事件消费位置 | 客户端数据层 |
| 界面交互状态 | 折叠展开、面板选择、输入草稿 | 界面状态层，按需持久化 |

React 根据组件参数和状态计算渲染结果，再把必要变化提交到实际界面。组件状态的保留还与组件类型、位置和键有关。[R10](05-references.md#r10) [R11](05-references.md#r11)

因此，稳定的业务标识有助于正确关联显示数据，但稳定 `key` 并不保证组件移到另一棵子树后仍保留本地状态。需要跨折叠重组保留的交互状态，可以按稳定标识放到更合适的状态层。

### 4.3 执行事实与折叠语法

Fold（执行过程折叠组）是展示结构。是否合并连续内容、长内容是否独立显示、最终回复怎样放置，属于产品的展示规则。ModelStep（模型调用步骤）则记录模型调用生命周期。

因此可以采用：一次任务包含若干调用与工具执行；投影按真实顺序形成折叠组；最终内容通过稳定引用关联任务。`finalContentRef` 表示对权威内容的引用，具体可以指向内容对象或内容集合，按消息协议确定。

单一权威事实源允许缓存、快照和派生视图存在。关键是这些副本有确定来源、更新规则和重建路径，避免互相独立地裁定同一事实。

**可直接使用的要求：**同一工具执行始终通过稳定身份关联请求、结果和状态；在相同事实、展示规则版本与相关交互输入下，实时消费与历史重建收敛到一致的业务展示。动画和滚动位置可以不同。

## 五、执行引擎：模型怎样参与一段持续工作

### 5.1 一段体验对应多个对象

用户体验中的“持续对话”可以这样映射：

```text
业务会话 Thread
├─ 任务轮次 Turn 1
│  ├─ 模型调用 ModelStep 1
│  ├─ 工具执行 ToolInvocation 1
│  └─ 模型调用 ModelStep 2
└─ 任务轮次 Turn 2
   └─ 后续执行
```

Agent Loop（模型与工具的执行循环）推进当前工作。Control Plane（控制接口层）受理发送、停止和恢复。Turn Controller（任务生命周期控制器）管理轮次状态。Ledger（权威执行记录）提供已提交事实。展示系统在执行循环没有运行时，也可以读取历史。

产品可以围绕连续对话组织，工程职责依据各自的生命周期分工。各模块可以集中于一个应用，也可以由框架提供。

### 5.2 模型输出的规范化

```text
模型服务原始响应
  → Provider Adapter（模型服务适配器）
  → 统一内容、工具调用、结束原因与错误
  → ModelStep 聚合和记录
  → 下一步执行决策
```

统一协议只承诺实际可获得的数据。提供方未暴露的内部推理、隐藏重试或服务端工具细节，应保留可观测边界。托管工具可能在模型服务端执行，需要记录服务端返回的状态和引用，而不是虚构本地工具进程。

采用 OpenAI Agents SDK（Agent 软件开发工具包）等现有框架时，应先核查它已经承担的循环、工具和会话能力，再确定应用补充哪些职责。官方运行、会话和上下文文档提供了这一核查入口。[R12](05-references.md#r12) [R13](05-references.md#r13) [R14](05-references.md#r14)

### 5.3 工具意图与实际执行

ToolCall（工具调用意图）表示模型提出操作。ToolInvocation（工具执行实例）记录系统管理的一次调用执行；其结果可以是完成、失败、拒绝或取消，并不都意味着外部进程成功启动。

```text
调用意图
  → 工具解析和参数校验
  → 权限判定与必要审批
  → 实际执行
  → ToolResult（结构化工具结果）
  → 进入后续模型上下文
```

模型上下文需要保留工具调用与工具结果的对应关系。通常需要同时保留发起工具调用的模型输出和匹配的结果；只附加孤立的结果文本可能破坏提供方要求的消息协议。

### 5.4 下一步如何决定

Continuation Decision（继续执行决策）综合规范化输出、待处理工作、取消状态和运行策略，选择执行工具、继续模型、等待审批或结束任务。它可以是普通规则函数，不必额外调用模型。

```text
准备上下文
  → 调用模型并记录结果
  → 判断下一步
     ├─ 有可执行工具：执行、记录、更新上下文
     ├─ 等待授权：保存状态并等待
     ├─ 满足继续条件：发起下一次模型调用
     └─ 满足终止条件：提交终态和已有产物
```

本系列建议把“过程结束”与“任务效果”分开记录。执行流程正常结束，仍可能报告无法完成目标；工具失败也可能成为模型调整方案的输入。最终自然语言回复、流程终态和验证结果可以互相引用，但各自表达不同事实。

**可直接使用的要求：**明确一次调用、一次工具执行和整轮任务的不同终态；结束依据结构化执行状态和策略，模型文本作为内容及决策输入。

## 六、可靠性：怎样知道哪些事已经发生

### 6.1 三种需要协调的状态

对话记录说明说过什么；执行记录说明系统确认到哪里；外部状态说明文件、进程、远程资源实际上发生了什么。

假设工具已修改文件，后台在保存结果前崩溃：数据库可能只有“运行中”，文件却已经变化。恢复系统需要表达“结果未知”，再核对实际环境。这是理解可靠性的关键场景。

### 6.2 事务、快照和检查点

Transaction（数据库事务）将相关数据库修改组织成原子提交单位；并发读写的可见性和冲突处理取决于隔离级别及具体操作。[R16](05-references.md#r16) [R17](05-references.md#r17)

可以把工具结果、完成状态、关联事件放在同一个事务中。大结果存放于外部对象存储时，需要先保存可校验内容，再提交引用，并设计孤立对象清理。普通数据库事务的边界通常不包含任意文件写入或第三方网络调用。

Snapshot（状态快照）便于查询或重建。Checkpoint（执行检查点）保存继续执行所需信息，例如已完成步骤、待处理工具、上下文引用、策略及配置版本。检查点帮助恢复执行位置；工具外部效果仍需独立确认。

### 6.3 四种“恢复”

| 操作 | 作用 | 核心约束 |
| --- | --- | --- |
| Replay（回放） | 用事实重建状态 | 不再次执行历史副作用 |
| Reconnection（重连） | 恢复通信与补齐数据 | 明确消费位置和历史保留范围 |
| Resume（继续执行） | 推进仍可继续的工作 | 从有效检查点和合法状态开始 |
| Retry（重试） | 再次尝试操作 | 判断重复副作用及幂等能力 |

Idempotency（幂等性）表示重复请求仍保持约定的业务效果。幂等键必须在实际处理边界生效。以 Stripe 为例，其接口文档明确了幂等键、重复请求和保存结果的具体行为；其他工具需核查各自的保证。[R19](05-references.md#r19)

对任意外部工具，建议区分可安全重试、可查询核对、结果未知需介入三种策略。副作用可能已经发生时，自动重试需要额外依据。

### 6.4 客户端补齐与并发控制

事件应有稳定身份和明确排序范围。游标可以是不透明值，也可以是序号；只有协议明确承诺连续且未过滤时，序号缺口才直接表示事件遗漏。快照位置、后续订阅、权限过滤和历史过期应形成完整约定。

Transactional Outbox（事务性发件箱）把业务修改与待发布事件一起提交，再由发布器投递；消费者仍需处理重复投递。[R18](05-references.md#r18)

同一任务被多个客户端控制时，可采用版本检查、锁或串行处理。多个任务修改同一文件时，还需工作区资源协调：会话标识不同并不自动产生文件隔离。进入多执行者场景后，还要处理执行所有权、过期执行者和迟到结果。

### 6.5 回退的三个范围

Rewind（历史回退）应明确作用于对话、执行分支还是工作区。回到旧消息后创建新分支，可以保留旧历史；文件恢复则需要文件快照或版本管理机制。已发送的消息、已发生的支付等外部效果，通常需要独立补偿规则。

**可直接使用的要求：**区分历史查看、执行继续和外部环境恢复；结果未知的操作先核对；控制冲突和共享文件冲突分别处理。

## 七、安全：用户目标怎样成为受约束的执行

### 7.1 四种不同角色

```text
用户表达目标
  → 模型提出操作
  → 可信策略确定许可
  → 执行边界落实约束
  → 审计记录实际结果
```

Authentication（身份认证）确认主体；Authorization（权限判定）判断主体能否对资源实施操作；Approval（人工审批）表达具体授权决定；Sandbox（隔离执行环境）限制实际可访问资源。OWASP 的授权指南强调最小权限、默认拒绝和在正确位置检查访问权限。[R20](05-references.md#r20)

本系列建议一次执行至少明确：主体、操作、资源、工作区、执行环境、有效许可及策略版本。AppContext（应用执行上下文）由可信入口构造，模型提供的身份或角色文本作为普通数据处理。

### 7.2 权限判定与执行约束

策略决策点回答能否执行；权限执行点使未经许可的操作无法通过入口。人工批准应绑定实际请求及范围，参数、目标资源或重要执行条件变化时重新判断。交易授权指南也强调授权内容与实际执行之间的一致性。[R22](05-references.md#r22)

“运行测试”是产品语义，实际效果取决于脚本内容和环境。npm 的脚本及生命周期机制意味着安装、测试等命令可能运行项目定义的程序。[R23](05-references.md#r23) 评估风险应结合访问资源、网络出口、凭据、可逆性和资源消耗。

### 7.3 外部数据与模型指令

Prompt Injection（提示词注入）涉及不可信内容影响模型行为。项目文件、网页和工具结果应保留来源与信任级别，并配合最小权限、输出检查和必要人工批准形成多层防护。[R21](05-references.md#r21)

MCP（模型上下文协议）提供工具和数据接入契约，工具声明与返回结果仍需纳入应用的信任和权限模型。具体协议能力以采用版本为准。[R24](05-references.md#r24)

“只读”也可能涉及敏感内容进入外部模型上下文。安全目标应同时覆盖允许读取什么、允许传往哪里、日志怎样脱敏、凭据怎样保存和撤销。

### 7.4 实际环境决定保证边界

独立进程主要划分运行和故障边界，强制隔离需要操作系统或受控执行环境配合。Windows、macOS、Linux 的支持能力应分别验证。产品承诺某种隔离时，需要记录实际配置、拒绝测试和机制失效时的处理方式。

**可直接使用的要求：**所有工具路径经过可信授权和实际执行控制；审批绑定具体范围；隔离失效时按明确策略安全处理；提供真实阻断证据。

## 八、怎样把知识变成定位问题的能力

以“工具执行完成，但界面没有输出”为例，先固定任务、执行身份、时间范围和软件版本，再寻找证据。

| 检查边界 | 观察什么 | 下一步 |
| --- | --- | --- |
| 工具执行 | 实际产生了什么输出 | 确认执行层结果 |
| 权威记录 | 结果是否保存并关联同次调用 | 检查提交及保留策略 |
| 传输/查询 | 客户端是否获得对应数据 | 检查过滤、补齐和接口 |
| 展示投影 | 视图模型是否包含输出引用 | 检查映射规则 |
| 组件 | 输入正确时是否显示 | 检查渲染及交互 |

沿数据链寻找首次可观察偏差，可以缩小调查范围。它不是自动证明单一根因的方法；并发、跨流时序和下游反向影响，仍需结合关联标识与运行证据分析。

调试要求可以压缩为：“围绕指定执行实例，沿结果记录、传输、投影和组件输入核对证据，定位首次偏差，修复对应责任边界，并覆盖实时与历史两条路径。”

## 九、怎样证明产品已经具备这些能力

测试应区分模型能力和执行系统正确性。Scripted Model（预设输出的模拟模型）可以固定调用序列；Mock Tool（模拟工具）可以固定结果；真实工具集成则检验外部环境。

建议建立一个最小验证组合：直接回答、调用一个工具、工具失败后继续、等待审批、停止与完成竞争、客户端重连、外部副作用后崩溃、历史回放、未授权操作。

| 证据层 | 证明什么 |
| --- | --- |
| 契约测试 | 请求、事件和错误遵守约定 |
| 执行轨迹 | 调用、工具和任务的因果关系正确 |
| 持久化回读 | 实际保存了哪些事实 |
| 外部检查 | 文件、进程或远程资源实际变化 |
| 产品端到端验证 | 用户从入口到结果的体验成立 |

模拟测试证明控制逻辑，真实集成证明环境连接，界面测试证明呈现。截图适合证明可见布局，协议测试适合证明数据结构；证据强度应与交付承诺匹配。

## 十、足以开始开发的共同基线

不必一次实现全部高级能力。对一个初期单 Agent 产品，可以先确认以下边界，再开展纵向功能切片：

```text
统一的任务入口
  → 一个明确的执行所有者
  → 一次模型调用与一次工具执行
  → 可查询的状态和结果
  → 桌面或命令行的真实展示
  → 停止、失败和重新进入历史的验证
```

共享接口、稳定身份、权限边界和事实记录应从开始就清楚；多执行者调度、复杂分支和远程部署则按实际目标加入。

最终需要形成的能力是：**能还原一条行为链，能预测一次变更影响哪些边界，能为异常提出可验证假设，能用证据判断交付。**这就是工程知识对低噪声开发的直接价值。
