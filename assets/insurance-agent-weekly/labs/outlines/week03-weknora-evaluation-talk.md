# 第三周专项分享大纲｜从标注 HTML 到 RAG 评估、问题归因与 Agent Harness

> 类型：供审阅的大纲（非演讲正文）  
> 所属：14周课程 Week 03 · D方向 Agent 编排  
> 目标时长：10–12分钟  
> 主题问题：**一份已经标注过的保险问答数据，如何帮助我们判断系统应该改哪里？**  
> 证据状态：上周标注数据已存在；WeKnora 本轮真实运行分数和专项归因结论待取得后补入。

## 贯穿案例与讲述原则

**用一条上周标注中的真实问题贯穿全篇。** 选择标准：有原问题、原系统回答、检索 Chunk、人工判断；最好还能观察到证据遗漏/无关结果混入，并有来源页线索。真实样本 ID 与可公开材料由实验核验后确定。可选第二条对照案例展示“找到了证据，但回答仍有误”。

整个分享依次回答：我们拿到了什么 → WeKnora 实际怎么跑 → 数据如何得到分数 → 分数如何帮助定位错误 → 为什么其中某类问题值得 Agent 改造 → 已有 Harness 如何支撑实现和测试。

始终标明系统身份、数据来源、真实结果与示意；WeKnora 原生指标属于 WeKnora 执行链路，历史保险系统回答的评分属于独立数据分析，两者分别报告。

## 01｜从上周的标注页面出发（约1分钟）

**开场问题：** 上周已经看过系统回答并做了标注，为什么本周还需要评估？

- 展示上周 HTML 的典型单题结构：Question（问题）→ Reference Chunks（参考检索块）→ Answer（实际回答）→ Annotation（人工判断）。
- 42题标注、317条参考 Chunk 的背景，仅用于交代已有数据规模；本周选少量样本实践。
- 说明人工标注提供的是可对照的真实样本和评价线索；第三周目标是把这些信息用于可重复的评分及错误定位。

**画面：** 1张脱敏 HTML 截图，箭头标出四类字段。  
**落点：** 直接复用上周产出，任务从人工观察转向系统测量。

## 02｜WeKnora 到底做了什么？（约2分钟）

**核心问题：** 它是一个问答程序，还是一个评估工具？两者是什么关系？

- WeKnora 本身有知识库与 RAG/Agent 能力：文档 → 解析/Chunk → 向量索引 → 检索 → 重排 → 生成。
- Evaluation（评估）是另一条围绕问答系统运行的链路：数据输入 → 建评估知识库 → 逐题执行检索/生成 → 对照参考数据计算指标 → 汇总结果。
- 官方评估当前主要通过 POST /api/v1/evaluation 创建任务，GET /api/v1/evaluation?task_id=... 查询；输入为 queries、corpus、answers、qrels、qas 五个 Parquet 文件。
- 指出每一步会产生什么输入和输出，为什么同样的题目在不同检索/模型配置下可以得到不同结果。
- 用一句话交代 Ragas（偏 RAG/答案质量的可扩展指标）与 DeepEval（兼顾 Agent 工具与轨迹评估）的补充位置。

**画面：** 1张双泳道图，上方 RAG 执行，下方 Evaluation 对照评分。  
**落点：** 理解接口背后完整执行过程，而不仅是返回数字。

## 03｜在本地怎样真正跑一次评估？（约1分30秒）

**核心问题：** 我做了什么操作，哪些事实证明它确实跑起来？

- 本地部署/模型配置的关键事实：实例版本、可用服务、使用的模型与语料范围（依据真实记录）。
- 实际操作：选用官方样本启动一次 POST → task_id → GET 轮询 → completed / failed 与返回的真实指标。
- 接入上周标注：从 HTML/JSON 直接读现成问题、回答、参考 Chunk 和人工判断；依据接口实际要求做技术格式转换。
- **两条实验路线**：
  - A：用 WeKnora 自带样本/满足输入要求的既有数据，评估 **WeKnora 的 RAG 链路**。
  - B：用原始 HTML/JSON 的历史答案和检索结果，借助现有项目评分器与适用指标评价 **保险系统的历史表现**。
- 每一步保留命令、数据版本、请求响应与配置；已有标签不具备的指标按实际可计算范围报告。

**画面：** 真实终端/接口返回截图 + “这份分数属于哪个系统”的清楚标注。  
**落点：** 将使用说明变成可重复的实验。

## 04｜怎样读懂真实评分结果？（约1分30秒）

**核心问题：** 结果高或低，意味着系统哪一部分表现怎样？

- 只重点讲3组：
  1. 检索“找到了没有”：Recall（召回）。
  2. 检索“排在哪里”：MRR、NDCG（首次相关结果排名、整体排序）。
  3. 生成“文本像不像参考答案”：BLEU/ROUGE；同时结合上周人工回答正确性判断其局限。
- 展示一张**填入真实数字**的精简指标表：实验对象、样本数、版本、三类指标、解释；对不满足输入条件的指标标注不可计算。
- 展示一条实际题目的检索结果与人工标注，说明总体分数如何对应单题现象。
- 保留参考语料和评测口径以解释不同批次分数能否比较。

**画面：** 1张实际指标表 + 1个问题的证据排序。  
**落点：** 得分是线索，逐题事实是诊断依据。

## 05｜从得分走向原因：哪里出了错？（约2分钟）

**核心问题：** 一道问题结果不好，究竟应该改数据、检索、生成还是决策？

按一个已核实的失败题目进行由外到内的检查：

1. 原始资料中是否存在需要的信息？——资料覆盖与 A（解析、分块、元数据）。
2. 正确 Chunk 已存在时，为什么没有进入高排名结果？——C（召回、重排）。
3. 如果必须枚举/比较业务事实，是否更适合结构化查询？——B（事实表、口径）。
4. 已找到充分证据仍答错？——Generation（生成与证据使用）。
5. 首轮证据不足时是否存在进一步查询的有效路径？——D（工具选择、查询拆解、继续与停止）。

允许“主要原因 + 共同因素”。从现有旧标注中挑选一条完整的、有原 PDF/Chunk 支持的案例。对 D 候选，区分“补充查询有机会带来更多有效证据”与“真实 Agent 已经证明提升”。

**画面：** 单题的「原问题/证据/输出/判断/归因」对照，附简短诊断树。  
**落点：** 归因分析比单一总分更能指导工程优化。

## 06｜提出优化并设计验证（约1分钟）

**核心问题：** 找出问题之后，下一步改变什么才有意义？

- A：改变文档表示或元数据；C：调检索/重排；B：补充事实查询；生成：改证据使用策略。
- D：针对“单次检索证据不足”提出最小 Agent loop：首次检索 → 判断缺失信息 → 改写或拆分查询 → 再次检索 → 判断是否继续/完成。
- 设计一项最小受控实验：保持资料/检索器和模型配置尽量一致，比较一次检索与允许补充查询时的证据覆盖、额外调用量、延迟。
- 以当前可验证的观察形成假设，留到第四周验证真实 Agent 决策效果。

**画面：** Fixed RAG vs Agent 多轮检索的对比图。  
**落点：** 第三周用证据提出改造方向，第四周用真实 Agent 证实效果。

## 07｜落到我负责的 D 方向和已建 Harness（约1分30秒）

**核心问题：** 为什么提出 Agent 改造，还需要 Harness？已有项目已经具备什么？

- Agent 负责决定下一步查询什么、是否继续；Harness（执行治理层）负责 Thread/Turn/Run 的受理、模型/工具调用管理、权限、预算、持久化与结果可追溯。
- 将完整链路展示为：用户提问 → Thread/Turn/Run → ModelStep → Tool Registry → 检索 ToolInvocation/Evidence → 继续或最终答复。
- 指出评估所需要的“检索输入、工具调用、证据、最终回答、配置版本”从已有运行事实中取得；这让后续系统评估和 Agent 优化有可复现依据。
- **与14篇已发布 Harness 分享的精确衔接**：
  - [第02篇：数据契约、运行事实与证据评测](../../02-contracts-and-runtime-facts.md)：理解 Evidence、来源与人工标注怎样对应。
  - [第03篇：请求受理、幂等与执行事务](../../03-request-admission-and-transactions.md)：知道一份用户请求如何成为可识别、可追踪的 Turn/Run。
  - [第12篇：测试与评测](../../12-testing-and-evaluation.md)：把协议正确、工具执行正确、模型决策质量和业务回答质量分开验证。
- 本地 D 工程已有 `tools/evaluation/` 与 M15 离线实验准备：说明已具备的评分/导出基础、已有合成测试证据以及仍要开展的真实业务评价。

**画面：** 1张 Harness 运行链路图，并在 Evidence/Tool/Run 位置标出评估数据挂载点。  
**落点：** WeKnora 帮我们理解与实践评估，D Harness 让后续自主 Agent 的真实执行可以被控制、记录和评测。

## 08｜结论与第四周任务（约30秒）

- **本周学会了什么**：理解 WeKnora 运行机制；真实完成小样本评估；把既有人工标注用于解释效果；识别了哪类问题需要进一步实验。
- **真实结果**：引用本周完成的运行状态、主要指标、一个有证据支持的案例；缺失项保持明确状态。
- **第四周要做的事**：针对已识别案例跑通最小自主检索循环，在固定基线下衡量证据覆盖改善和额外代价。

结束句建议：**第二周我们记录系统哪里表现不好；第三周把表现变成可测量、可解释的工程问题；第四周验证 Agent 能否据此更好地行动。**
