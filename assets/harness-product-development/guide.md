## 技术实现、架构设计与模块开发顺序指南

> 面向产品负责人、软件工程师及 Coding Agent（编程智能体）。以通用 Harness API（Agent 执行控制接口）组织产品能力，使桌面、命令行、网页和业务系统能够共同使用可观察、可控制、可恢复的执行系统。

## 摘要

完整 Agent 产品需要把用户目标转化为受管理的执行，再把真实结果转化为可理解的体验。模型调用、工具执行、持续对话、历史分支、状态同步、权限与安装发布共同构成这条链路。

本指南以 Harness API 为稳定边界：上层客户端通过命令、查询、等待和订阅表达需求；下层执行引擎通过适配器接入模型、工具、存储和运行环境。开发顺序由业务契约及模块依赖决定，交付结论由实际证据支持。

文中提供一套参考契约和本地双端实现配置。对象名称、路径、状态和默认值属于本指南的设计约定；采用者应在自己的项目中确认并版本化。公开框架机制在相关段落引用第一方资料。示例轨迹、接口和验收目标是设计材料，项目实际完成状态需由项目测试填写。

## 1. 用产品行为界定完整性

### 1.1 一条贯穿系统的场景

用户选择一个工作区，发送“检查项目、修复问题并验证”。Agent 读取内容、提出工具调用、在授权范围内执行并显示进度。用户能够从另一客户端接入同一任务、处理审批、停止执行、查看结果和历史，再按约定继续任务或从历史建立新分支。

将场景转换为系统职责：

| 用户行为 | Harness 对外能力 | 支撑模块 | 验收证据 |
| --- | --- | --- | --- |
| 创建工作空间和对话 | 工作区、会话管理 | 身份上下文、领域存储 | 可查询的稳定对象 |
| 发送任务 | `send` | 命令受理、任务调度、执行驱动 | 回执与实际执行关联 |
| 观察过程 | `snapshot`、`subscribe` | 事实记录、展示投影 | 实时与历史一致 |
| 等待最终处理结果 | `wait` | 条件观察与结果查询 | 等待目标和返回原因明确 |
| 批准工具操作 | `decideApproval` | 授权、审批、执行器 | 批准内容与实际操作一致 |
| 停止、继续 | `stop`、`resume` | 状态机、取消、检查点 | 实际停止与恢复证据 |
| 编辑、回到历史 | `editAndRun`、分支查询 | 版本关系、上下文选择 | 原历史保留、新路径可追踪 |
| 使用产物 | 产物列表与读取 | 结果存储、访问控制 | 内容、来源和权限可核对 |

API（应用编程接口）既可以是进程内接口，也可以通过网络或进程消息提供。表格描述业务能力，具体传输保持可替换。

### 1.2 三层适用范围

**通用产品契约**规定身份、执行控制、事实和结果的含义。**部署配置**规定执行者、文件和数据库在哪里。**参考技术栈**提供一种实现选择。

本地单用户产品可以采用一个后台和一份本地数据库；托管产品可以增加租户、组织、配额和多执行者。采用相同契约并不意味着它们提供相同隔离或恢复等级，应通过能力发现接口如实声明。

## 2. 先把体验整体映射到工程模型

用户感受到的“连续对话”是一种体验组织方式。系统需要分别表达长期会话、一次任务、一次实际执行、模型调用、工具操作和界面状态。

| 视角 | 关心什么 | 在本指南中的表达 |
| --- | --- | --- |
| 产品体验 | 用户如何连续完成工作 | 对话、任务控制、工作区与结果 |
| 领域对象 | 哪些事实有独立身份和生命周期 | Thread、Turn、Attempt、Invocation |
| 模块职责 | 谁接收、决定、执行和记录 | 控制服务、执行驱动、工具系统、存储 |
| 运行部署 | 谁在何处运行和通信 | 客户端、本地后台、远程服务、工具执行环境 |
| 数据展示 | 信息怎样成为可见内容 | 事实 → 投影 → 视图模型 → 组件 |

Thread 是业务会话，不是操作系统线程。Agent Loop 是模型和工具交替推进的执行机制；历史查看、权限管理和客户端重连在循环没有运行时仍可发生。

一个代码模块可以和其他模块共享进程，一份代码也可以被多个进程分别加载。产品要共享正在运行的任务时，需要共同的执行所有者；仅共享源代码并不能建立这一关系。

**指导开发的表达：**先确定体验、权威事实和生命周期，再确定模块及部署。用同一用户路径反向检查架构是否保留了原始目标。

## 3. 总体架构：围绕稳定接口组织变化

```text
桌面客户端 / CLI 命令行 / TUI 终端界面 / Web 网页 / 业务集成
                         |
              HarnessClient（业务客户端）
                         |
        通用 Harness API：命令 / 查询 / 等待 / 订阅
                         |
          身份与资源校验、命令幂等、状态转换
                         |
         Turn Controller（任务生命周期控制器）
                         |
            RuntimeDriver（执行引擎适配器）
              /                         \
     SDK 执行循环                    自有执行循环
              \                         /
       模型接入、上下文、工具授权与实际执行
                         |
      Ledger（权威记录）及状态、检查点、内容与产物
                         |
     Projection（展示投影）→ 客户端数据 → 界面组件
```

这是职责与数据关系图。运行期间控制、执行、记录和投影会反复协作，不能把全部方框理解为一次性顺序调用。

### 3.1 各层输入输出

| 模块 | 输入 | 输出 | 主要所有权 |
| --- | --- | --- | --- |
| 客户端 | 用户操作、快照和事件 | 命令、局部交互状态 | 草稿、当前选择、展开状态 |
| 控制服务 | 已认证的业务请求 | 回执或结构化错误 | 命令受理及合法转换 |
| 任务控制器 | 已受理任务与控制命令 | 执行启动、取消、最终处理结果 | 当前执行所有权 |
| 执行驱动 | 指定上下文、策略和状态引用 | 规范化执行信号 | 对底层执行机制的适配 |
| 工具系统 | 工具意图与可信上下文 | 实际结果、许可与副作用记录 | 实际执行入口 |
| 记录与存储 | 待提交事实 | 可查询记录和检查点 | 已提交业务事实 |
| 展示投影 | 事实及规则版本 | 视图快照与增量 | 派生的展示语义 |

### 3.2 三个接口边界

**公共 Harness API**面向产品与集成者，暴露会话、任务、控制、历史和结果。

**RuntimeDriver**面向内部执行引擎，封装 SDK 或自有循环。公共接口不直接暴露 SDK 的对象图、类实例和序列化状态。

**ToolExecutor（工具执行器）**面向实际工具环境，落实身份、许可、资源范围和输出处理。执行引擎使用这道边界或提供可验证的等效控制。

这三个边界允许更换界面、SDK、模型或执行环境时，将变化限制在对应适配处。

## 4. 领域模型与稳定身份

### 4.1 核心对象

| 对象 | 中文含义 | 关键关系 |
| --- | --- | --- |
| Workspace | 工作区 | 绑定资源范围及执行环境 |
| Thread | 业务会话 | 组织长期历史、分支和任务 |
| Branch | 对话分支 | 指定被采用的上下文路径 |
| Turn | 一轮用户任务 | 绑定原始输入、执行尝试与结果 |
| RunAttempt | 一次实际执行尝试 | 记录本次启动到停止或处理结束 |
| ModelStep | 一次可观察模型调用 | 关联模型输出与工具意图 |
| ToolCall | 工具调用意图 | 使用 `intentId` 标识 |
| ToolInvocation | 工具执行实例 | 关联意图、许可、运行与结果 |
| Approval | 审批记录 | 绑定主体、请求内容、范围和有效条件 |
| ContentItem | 权威内容项 | 保存文本、结构化输出等实际内容 |
| Artifact | 产物 | 绑定版本、来源、访问方式及保留策略 |
| Checkpoint | 执行检查点 | 保存继续执行所需的兼容状态 |

ToolInvocation 可以先处于等待审批或待执行状态，拒绝也是有效处理结果；是否实际启动外部进程由独立字段和事件表示。

### 4.2 模型调用与重试

本指南约定一个可观察的模型 API 调用对应一个 ModelStep。一次逻辑调用有多个可观察尝试时，分别记录并通过重试关联连接。SDK 内部不可观察的重试标明可观测范围，统计报表不推算不存在的证据。

提供方的 `call_id` 保留为来源关联，产品使用自己的 `intentId`。工具进入受管理的调用流程时分配 `invocationId`，它可以先处于等待审批或待执行状态；实际启动由 `tool.started` 等事实确认。需要跨重试去重的业务动作使用稳定 `operationId`。这些标识用途不同。

### 4.3 内容只确立一个权威来源

最终回答通过 `finalContentRef` 引用已保存的内容项或内容集合。视图可以缓存文本，但其来源和重建方式明确。

```json
{
  "turnId": "turn_21",
  "finalContentRef": {
    "stepId": "step_54",
    "itemKey": "content_1"
  }
}
```

有些任务产生文件而没有自然语言结论，引用可以为空并返回产物。已停止任务也可以保留部分内容。内容存在、流程结束和任务目标达成是分别记录的事实。

## 5. 通用 Harness API 的能力面

详细请求、响应和错误见[接口契约参考](api-contract.md)。这一节说明各类能力对产品的意义。

### 5.1 能力发现与对象管理

`getCapabilities` 返回协议版本、支持的控制能力、事件格式、执行环境及具体限制。客户端按能力配置界面，不根据某个 SDK 名称推断可以恢复或回滚。

管理接口提供工作区注册、会话创建与列表、分支查询、重命名和归档。注册工作区只是建立资源关系；实际文件访问仍由运行时授权检查。

`archive`（归档）改变列表呈现和接收新输入的规则，`delete`（删除）涉及保留策略、任务活动状态和引用清理，应作为不同操作处理。

### 5.2 执行与控制

核心方法为 `send`、`wait`、`stop`、`resume` 和 `decideApproval`。历史能力采用 `forkBranch`、`editAndRun` 和指定位置的查询。

所有改变业务状态的命令包含客户端生成的 `commandId`。后台在可信主体及操作范围内保存请求摘要与回执；重复请求返回原结果，请求内容变化返回冲突。

请求中的用户或组织标识只能用于选定一个已经授权的范围。实际主体来自可信连接上下文，服务端独立校验对象归属。

### 5.3 状态与内容读取

查询接口分别提供任务状态、执行尝试结果、审批详情、会话快照、事件订阅和产物读取。原始诊断轨迹具有单独权限；普通界面仅获得其有权使用的结果和脱敏内容。

文件上传先完成大小、类型、内容及归属校验，再把受控引用加入任务。产物通过稳定标识读取，临时下载地址只是访问方式，不是产物身份。

### 5.4 公共接口与传输

进程内调用、IPC（进程间通信）、HTTP（请求响应协议）和其他传输可以实现同一契约。HTTP 状态码遵循对应语义，错误体可采用 RFC 9457 的问题详情结构；业务错误仍需要明确的稳定代码和恢复提示。[S01](references.md#s01) [S02](references.md#s02)

API 版本、事件结构版本、展示规则版本及数据库版本分别管理。能力变化和检查点兼容性通过握手与版本检查显式处理。

## 6. 发送、同步等待与任务预算

### 6.1 受理点必须清楚

`send` 的受理成功发生在输入、任务、执行尝试、幂等回执和待执行记录可靠提交之后。调度器消费持久化队列或等效记录；通知信号可以优化唤醒，但任务存在性由存储确定。

这样，响应丢失后，客户端仍可使用相同命令标识查询或重试，而不会因为重新点击发送建立第二个任务。

### 6.2 两种响应模式

`responseMode: "async"` 返回已经持久化的回执。`responseMode: "sync"` 先受理同一个命令，再等待该回执绑定的执行尝试产生最终处理结果。

默认同步等待不设置较短的业务等待期限。等待审批仍属于执行中的等待阶段，不能当作任务完成返回。客户端可以显式选择 `settled_or_attention`，在需要人工输入时先得到当前状态。

HTTP 连接、代理或工具宿主可能有单次等待上限。客户端库应复用任务标识续接查询或长轮询，维持逻辑上的同步等待；传输到期不能伪装成任务已经完成。

### 6.3 等待目标绑定执行尝试

同一 Turn 停止后可以产生新的 RunAttempt。每个等待者绑定明确的 `attemptId`，从而避免一个短暂的停止状态因快速恢复而被旧等待者漏掉。

一次尝试的最终处理结果为 `completed`、`failed`、`stopped` 或 `recovery_required`。后者表示自动推进已中断且仍有待核对事实，必须携带未确认的外部效果范围。它不表示所有远端动作已经终止。

### 6.4 五类时间分别建模

| 时间 | 控制对象 | 到期处理 |
| --- | --- | --- |
| 连接请求时限 | 一次网络或进程通信 | 返回连接问题，可重连 |
| 调用方等待期限 | 本次 `wait` | 返回超时状态，任务继续 |
| 活动执行预算 | 模型和工具主动运行 | 按策略停止或失败 |
| 绝对任务期限 | 含排队与人工等待的总生命周期 | 按明确任务策略处理 |
| 工具执行/清理时限 | 单个外部操作 | 取消、核对或结果未知 |

活动预算是否计入排队和审批必须写明。客户端只能在授权策略允许的范围内选择预算。时间戳由可信服务记录为 UTC；显示按客户端时区转换，执行顺序由提交关系决定，耗时优先用单调时钟测量。

## 7. 状态机：谁有权结束一次工作

### 7.1 参考状态

```text
queued（已排队） → running（运行中）
                       ├→ waiting_approval（等待审批） → running
                       ├→ stopping（停止中） → stopped（已停止）
                       ├→ completed（流程完成）
                       ├→ failed（执行失败）
                       └→ recovery_required（需要恢复处理）
```

RunAttempt 一旦形成最终处理结果，该结果作为历史记录保持稳定。审批暂停和正常审批继续可以属于同一次尝试；从已停止或故障恢复状态重新启动则建立新尝试。

Turn 的当前状态引用最新尝试。`resumable` 是服务端检查检查点、分支位置、权限和环境后给出的能力，不仅由状态名称推导。

### 7.2 停止的真实工作

控制服务记录取消意图；执行者停止安排新动作，尝试取消模型请求，通知工具执行器清理相关操作，收集已经发生的结果，最后提交处理结论。

`stopped` 要求受控执行已停止且已知结果完成收尾。无法确认的远端操作或孤儿进程进入 `recovery_required`，相应工作区保持隔离或受限，直至核对结束。

停止与正常完成竞争时，服务端通过状态条件写入或串行仲裁形成一个有效结果。迟到消息仍可作为事实入账，但旧执行者不能借迟到结果启动新动作。

### 7.3 继续的前置条件

继续执行需要合法的基准尝试、兼容检查点、仍有效的资源权限、符合策略的工作区版本，以及没有冲突的活动任务。

原任务后方已经出现依赖性新历史时，应说明继续会改变什么上下文。参考配置要求在原分支前沿继续，或明确建立分支，避免把旧执行结果插入已经确定的新上下文。

`completed` 表示流程正常收尾；任务目标是否已达到由 `taskOutcome` 及验证证据表达，例如“完成检查但仍发现错误”。模型自然语言声明是内容，不独立决定执行终态。

## 8. 执行内核与 SDK 接入

### 8.1 从接口反推内部驱动

RuntimeDriver 需要完成开始执行、发出规范化事件、响应停止、导出检查点和从受信状态继续。它的输出先进入产品记录层，再形成对外事实。

```text
公共 send / resume
  → 任务控制器选择已授权配置
  → 构建指定分支上下文
  → RuntimeDriver
  → 模型与工具交互
  → 规范化内容、调用、审批、结果和结束信号
  → 产品事务提交
```

有两种内部实现方式。完整 Agent SDK 已提供循环时，驱动复用它并接入工具与事件钩子；只使用模型 API 时，由自有循环处理规范化工具调用和继续决策。两种方式对公共接口保持相同承诺。

### 8.2 一次模型与工具闭环

```text
创建 ModelStep
  → 流式收集模型实际输出
  → 保存模型消息与工具调用意图
  → 完成本次模型调用记录
  → 校验、授权并执行工具
  → 保存匹配的 ToolResult
  → 将模型工具调用和匹配结果一起纳入下一次上下文
  → 继续调用或提交任务结果
```

默认参考实现等待工具输入完整并通过校验后才启动副作用。实现支持提前处理时，必须证明输入已稳定、权限有效并且执行关系可记录。

### 8.3 SDK 对照必须做成验证

OpenAI Agents SDK 的运行机制包含模型调用、工具执行和后续循环；其公开文档可用于验证这一类适配方案。[S04](references.md#s04)

SDK 流结束可能表示等待审批，也可能仍有清理需要完成。公开流式文档要求等待 `stream.completed`，并在继续未完成轮次时复用运行状态。产品必须进一步映射为自己的等待、停止和完成状态。[S05](references.md#s05)

需要验证的接入项包括调用边界、工具身份、嵌套执行、重复事件、取消语义、审批暂停、状态序列化及上下文所有权。任何无法观测或无法控制的能力，写入驱动的能力说明。

### 8.4 托管工具的控制范围

工具可能在提供方服务器运行。此时保存提供方调用标识、实际返回状态及访问策略，避免虚构本地进程记录。

公共能力应说明哪些工具可以在执行前审批、哪些可以取消、哪些支持结果查询。产品要求强制审批而驱动无法落实时，禁用对应工具配置或选择可控执行方式。

## 9. 上下文、记忆与持久化的职责

### 9.1 三种信息分开管理

**会话事实**保存用户输入、模型输出和工具结果。**模型上下文**是为下一次调用选择、压缩和组织的信息。**长期记忆**是跨任务可使用且有来源与适用范围的知识。

上下文构建器从指定分支读取事实，保留工具意图和结果的协议关联，过滤敏感内容，再应用明确的预算和压缩策略。压缩结果记录输入范围、版本与来源，使以后能够解释模型看到了什么。

分支选择变化时，提供方会话 ID 或响应链也必须对应正确的历史位置。SDK、本地存储和提供方托管历史之间需要一个明确所有权模型。OpenAI Agents SDK 的会话文档提供会话存储接口及相关选项，但恢复承诺仍应以采用版本验证。[S07](references.md#s07)

### 9.2 应用上下文不等于模型输入

AppContext（可信应用上下文）保存主体、租户、工作区、执行环境、策略版本和凭据引用。它由服务端构造。模型只接收获准的任务数据。

SDK 可能把部分应用上下文纳入序列化状态，因此凭据应按引用重新获取。应用本地上下文与模型可见上下文的差异可参考 SDK 文档。[S08](references.md#s08)

### 9.3 RAG 与记忆作为能力接入

RAG（检索增强生成）可以通过检索服务和工具提供资料，长期记忆通过明确读写接口管理。两者使用同一授权、来源、结果记录和展示链路。产品根据需要选择检索或记忆能力，公共任务控制接口保持稳定。

## 10. 工具、安全与审批

### 10.1 从意图到受控执行

```text
模型 ToolCall
  → 注册解析、参数与资源校验
  → 可信主体 + 操作 + 资源 + 环境的权限判定
  → 必要的人工审批
  → 执行前重新校验有效条件
  → ToolExecutor 落实文件、网络和进程约束
  → 结果、外部效果和审计记录
```

Authorization（权限判定）和 Approval（人工审批）承担不同作用。审批者只能授予自己有权决定的范围。最小权限、默认拒绝及每次资源访问校验可参考 OWASP 指南。[S14](references.md#s14)

审批记录至少关联请求摘要、工具及配置版本、工作区、执行环境、审批主体、有效期和策略版本。两个客户端同时操作同一审批时，使用版本与一次性消费规则决定结果。

### 10.2 真实执行约束

Shell（命令解释环境）和测试脚本可以启动其他程序。即使使用参数数组和 `shell: false`，所启动的程序仍可能执行任意项目代码。执行器应限制环境变量、工作目录、网络出口、凭据、输出规模和进程树。

Node.js 的子进程接口提供程序启动及标准流能力，取消与进程清理仍需结合平台实现和验证。[S17](references.md#s17)

读取也会涉及保密性：敏感文件可能进入模型上下文、日志或远程工具。把允许读取和允许外发作为分别检查的条件。

### 10.3 外部内容与权限

Prompt Injection（提示词注入）可能通过文件、网页或工具结果影响模型后续决策。防护结合来源标记、上下文处理、最小权限、执行控制和人工确认，而非单靠提示词。[S15](references.md#s15)

MCP（模型上下文协议）工具同样经过统一资源与权限管理；其工具声明和结果不能自行授予权限。实施时固定实际协议版本并核对工具定义。[S16](references.md#s16)

### 10.4 执行环境能力分级

可信本地模式表示用户明确授权运行自己的代码；受限工具模式约束文件与命令能力；强隔离模式需要操作系统、容器或虚拟化机制的真实验证。每种模式写明防护对象和剩余权限。

后台凭据、模型密钥和服务端检查点不发送给普通界面或工具。以 SDK 审批状态为例，序列化状态本身不认证提交者，必须保存在受控存储或进行完整性、归属和重放校验。[S06](references.md#s06)

## 11. 事实记录、事务与副作用恢复

### 11.1 权威记录的最小形态

采用状态表加事件表即可建立可追溯记录；是否完整采用 Event Sourcing（事件溯源）由项目需求决定。数据库中明确哪个记录具有权威性，哪些是派生索引和缓存。

建议分组保存工作区与分支、任务与尝试、模型调用、工具意图与结果、审批、命令回执、内容、检查点和事件。

### 11.2 事务提交的边界

需要共同成立的状态、结果引用和事件在一个事务中提交。大结果先写入可校验对象，再提交引用；孤立对象和过期内容按保留策略清理。

事务的隔离级别和条件更新决定并发下的实际保证。采用事务并不自动消除写入竞争，应为状态转换和唯一性定义约束。[S11](references.md#s11)

任务受理与待执行记录同事务提交，结果完成与待发布事件同事务提交。Transactional Outbox（事务性发件箱）是协调存储和消息发布的一种方式，发布端与消费端仍要处理重复投递。[S12](references.md#s12)

### 11.3 工具结果未知时

```text
记录即将执行 → 外部副作用完成 → 保存结果之前崩溃
```

恢复时数据库中缺少完成记录，只说明缺少证据。工具按自身能力执行安全重试、幂等调用、外部状态核对或人工处理。

稳定 `operationId` 只有在实际副作用边界被识别和约束时才形成幂等保证。文件修改可以使用基准版本与条件补丁；远程资源可以查询业务操作标识；任意命令则可能无法自动判断全部效果。

### 11.4 检查点与恢复入口

检查点记录驱动及 SDK 版本、Agent 配置摘要、工具版本、上下文引用、分支位置、待决工具和环境信息。恢复前验证所有权、完整性、权限、配置兼容性与工作区状态。

无法恢复的检查点保持可解释状态，允许从安全输入创建新执行。格式兼容不等于副作用安全，二者分别验收。

## 12. 并发、所有权与资源协调

### 12.1 三种并发分别处理

**同一命令重试：**使用幂等回执。

**同一任务控制：**使用目标尝试、状态版本及条件写入。

**不同任务修改同一资源：**使用真实工作区身份、锁、工作树或冲突检测。

不同会话名称、路径别名、大小写差异或不同挂载路径，不应绕过同一底层资源的协调。跨 Windows 与 WSL 访问同一目录时尤其需要明确资源映射。

### 12.2 参考调度策略

参考配置每个分支最多一个活动任务；同一可写工作区中的任务串行进入。等待审批时保留资源占用，或在释放后于恢复前重新验证工作区与批准条件。选择哪一种策略应在产品中公开表达。

全局并发、模型请求数、工具数和资源预算各自限流。逐字内容事件不应持续推动用于用户控制的版本号，避免普通流式输出造成无意义的操作冲突。

### 12.3 多执行者扩展

分布式执行需要 Lease（带期限的所有权）、心跳和 Fencing Token（阻止旧执行者写入的代际标识）或等效机制。过期执行者可能仍在运行，单纯把数据库所有者改掉不足以防止旧进程继续产生副作用。

资源执行入口应验证当前代际；无法验证的外部效果需要更强隔离或核对策略。未确认清理的工作区保持受限，不立刻交给新的写入任务。

## 13. 快照、事件流与客户端一致性

### 13.1 一条事实、两类输出

执行事件提供业务事实，展示事件提供派生视图。两者由同一来源生成，但具有不同权限、版本和消费规则。客户端通常选择一种权威同步路径，避免把两个流的文本增量重复应用。

本指南的可恢复基础格式是有界的事件或视图批次：包含批次身份、前游标、后游标、协议版本和完整数据。收到完整批次并原子应用后，客户端才推进自己的已应用游标。

### 13.2 正确的快照起点

快照必须声明它真正包含的提交位置。异步投影落后时，返回投影实际位置，不冒称最新事实位置。

客户端加载位置 S 的快照，再请求 S 之后的数据。服务端通过持久记录补齐至当前，再持续发送；实时通知是唤醒机制，缺一次通知不能永久漏掉已保存事件。

游标绑定访问主体、会话/分支、过滤范围和协议版本。游标过期、范围不匹配或权限变化时，返回重新授权或重建要求。过滤后的序号不一定连续，客户端不能仅凭数值缺口推断数据丢失。

### 13.3 SSE 能提供什么

SSE（服务器发送事件）定义事件格式、事件标识和重连机制；它不替应用保存历史，也不确认界面已应用数据。`Last-Event-ID` 反映传输层观察位置，应用恢复应使用已成功应用的游标。[S03](references.md#s03)

需要授权头及精细游标控制时，可使用基于 `fetch` 的读取器。使用浏览器 Cookie 认证时，相应的跨站请求保护和来源限制单独配置。

### 13.4 UIMessage 适配

UIMessage（面向界面的消息结构）可以作为展示适配格式。AI SDK 的流协议提供文本、工具及自定义数据片段等能力。[S09](references.md#s09)

任务状态、同步游标和展示规则属于产品扩展约定。消息的 `finish` 或传输的 `[DONE]` 不直接等于 Turn 完成。已有 `useChat` 等客户端能否从快照中途继续消费，必须以实际版本验证；原生聊天钩子不自动承担完整会话补齐协议。

建议把可恢复同步器作为共同基础，再适配 UIMessage 组件。重复片段依照稳定身份、版本或内容偏移合并。

### 13.5 大输出与背压

Backpressure（背压）用于控制生产速度与消费能力不匹配。为订阅缓冲设置上限，慢客户端可断开并重新从已应用游标读取，后台不为其无限积压内存。

文本采用分块提交；工具日志存为可分页内容；历史按页或窗口加载。临时动画与心跳可以丢弃，已承诺保存的内容必须具备恢复路径。

## 14. 从事实到完整界面

### 14.1 展示投影负责什么

投影根据有序事实、上下文归属和规则版本生成 Turn 视图、内容项、工具单元、审批及产物引用。

Fold（执行过程折叠组）是展示结构。一个折叠组可以包含多个模型和工具相关展示项；模型步骤的结束条件继续由模型调用生命周期决定。

相同事实、规则版本和必要输入，实时增量与历史重建应形成等价的最终展示语义。动画、选择和滚动位置允许采用客户端独立状态。

### 14.2 组件身份与本地状态

工具单元通过 `invocationId` 关联输入输出，最终内容使用 `finalContentRef`。组件移动、折叠重组或分页时，需要保留的交互状态放到稳定身份索引的客户端状态层。

React 的状态保留与组件类型、位置和键有关；单有稳定业务标识不能保证跨父级移动后仍保留组件本地状态。[S10](references.md#s10)

### 14.3 可观察内容的来源

模型输出、工具输出、系统状态和派生摘要在数据中注明来源。进度可以来自“工具已启动”等真实信号，缺少模型推理内容时不生成假想推理。

若调用模型生成语义化进度摘要，记录它是派生描述，并保持实际工具状态与原始结果可查询。显示文案不能成为生命周期裁判。

## 15. 桌面、CLI 与业务集成的接入设计

### 15.1 桌面参考实现

Electron（桌面框架）主进程管理窗口及系统接口，渲染进程承载 React 界面，Preload（预加载脚本）建立受限桥梁。[S19](references.md#s19)

```text
React 操作 → 限定桥梁 → 主进程 HarnessClient → Harness API
后端快照/批次 → 主进程 → 界面同步器 → 组件
```

后台连接凭据由可信部分管理。验证 IPC 发送方与参数，限定导航、新窗口和外部链接，开启适当的上下文隔离及进程沙箱。Electron 安全指南提供这些基础要求。[S20](references.md#s20) [S21](references.md#s21)

预加载桥梁传递可序列化结果、回调通知或消息端口，不直接传递跨进程不可用的异步迭代器和 SDK 实例。

### 15.2 CLI 与终端交互

CLI（命令行接口）同时服务人和程序。Commander.js 可承担命令解析，Ink 可提供 React 风格的 TUI（终端交互界面）。[S22](references.md#s22) [S23](references.md#s23)

```text
agent chat --thread thread_1
agent run "检查项目" --workspace workspace_1
agent task watch --turn turn_1 --attempt attempt_1
agent task stop --turn turn_1 --attempt attempt_1
agent task resume --turn turn_1 --from-attempt attempt_1
```

这些是参考命令。各入口调用同一个 HarnessClient，统一错误、等待和事件消费。机器模式按约定输出 JSONL（每行一个 JSON 对象），诊断写入 stderr（标准错误流），退出码说明实际结果。

无人值守模式默认在需要人工介入时返回任务身份及明确退出原因；用户显式选择等待审批时，继续等待。退出观察界面、管道关闭与停止后台任务分别定义，避免自动化脚本意外取消共享任务。

### 15.3 双端体验清单

桌面需要输入、历史、工具详情、审批、产物与连接状态。终端需要中文输入、粘贴、多行文本、终端尺寸变化、输出限量及清晰快捷键。两端可以拥有不同布局，但对同一任务的状态和控制结果保持一致。

原生文件选择、剪贴板和窗口属于平台接口；任务控制属于 Harness API。分开这两类能力，可以让网页或其他集成者使用相同任务系统。

## 16. 历史编辑、回退与工作区恢复

### 16.1 历史作为可追溯路径

```text
Turn 1
  ├─ Turn 2 原版本 → Turn 3
  └─ Turn 2 新版本 → 新执行
```

编辑历史用户消息后运行，从该用户输入之前的安全上下文位置创建分支，并原子提交新输入、任务与回执。旧输入和旧结果保持可查询。

安全位置要保留模型工具调用与结果的协议完整性。第一版可只允许已稳定的用户消息边界，其他粒度通过能力发现显式开放。

### 16.2 回退预览与执行命令

点击回退按钮可以先切换本客户端的历史预览和输入草稿。取消预览恢复原选择。只有用户确认发送时才调用建立分支或编辑运行接口。

版本序号表示可选择的历史版本，服务器使用稳定分支和内容身份关联。客户端不以列表下标替代业务对象。

### 16.3 工作区状态单独处理

对话回退改变模型上下文路径；工作区回滚改变文件。需要后者时，先预览文件差异、检查未保存或外部修改、取得授权，再执行并记录结果。

发送通知、创建远程资源等外部效果按独立补偿规则处理。新分支已经执行后的“取消”应说明是在切换视图、停止新任务还是回滚文件。

## 17. 部署、身份和商业扩展

### 17.1 三种部署配置

| 配置 | 运行方式 | 适用目标 |
| --- | --- | --- |
| Embedded（嵌入式） | 执行随单个应用存活 | 独立本地使用、快速原型 |
| Local Daemon（本地常驻服务） | 多客户端连接同一后台 | 双端共享任务、窗口退出后继续 |
| Remote（远程服务） | 网络连接统一执行平台 | 多设备、组织协作、托管运行 |

本地双端参考配置选择一个常驻后台、一个执行所有者及本地数据库。远程配置可以保留公共契约，再增加租户隔离、持久队列、执行者调度和网络授权。

### 17.2 本地发现与后台生命周期

客户端发现当前用户的后台连接记录，校验协议及实例身份，未运行时通过统一启动器启动。并发启动用操作系统锁或等效机制仲裁，并校验陈旧锁和进程代际。

关闭窗口或观察客户端默认只断开连接。停止后台使用单独的管理操作，先停止受理、处理活动任务、保存检查点，再退出。后台重启后先核对未完成效果，再开放可能冲突的写入任务。

回环监听仍需要连接认证、主机和来源校验、限流与凭据保护。同用户恶意进程、凭据窃取等威胁需要另外的安全边界；“本机接口”不是完整授权依据。

### 17.3 跨平台与 WSL

工作区显式关联执行环境。Windows 路径由 Windows 执行器处理，WSL（Windows 的 Linux 子系统）路径由对应 Linux 执行器处理。权限、命令查找、取消及文件身份分别验证。

SQLite 的 WAL（预写日志）允许读写并行，但同一时刻只有一个写入者，并要求相关进程位于同一主机，不适合作为跨主机网络共享数据库。[S13](references.md#s13) 本地配置由后台独占数据库访问接口；跨环境客户端通过 API 连接。

### 17.4 组织、计费与配额

认证确认访问者，资源授权确认可操作对象，权益与预算确定本次任务可使用的能力和资源。它们在请求受理与执行边界检查，业务结果按实际消耗计量。

支付核验、权益授予和模型执行属于不同生命周期。商业扩展通过可信 AppContext、授权和预算接口接入 Harness，避免将“已登录”或“已付款”直接等同于任意工具执行权限。

## 18. 存储目录、模块依赖与参考选型

### 18.1 逻辑工程结构

```text
apps/
  desktop/          桌面入口、主进程、预加载、界面
  cli/              命令、终端交互、机器输出
  harness-host/     服务启动、路由、发现、管理
packages/
  contracts/        请求、结果、事件和运行时校验
  domain/           对象、状态规则和不变量
  client/           传输适配、等待、同步和错误
  application/      命令处理、查询和任务调度
  runtime/          执行驱动、上下文及 SDK 适配
  tools/            工具、许可与执行环境
  persistence/      事务、队列、事件和检查点
  presentation/     展示投影及消息协议适配
  platform/         文件、进程、凭据和系统差异
  testing/          模拟模型、模拟工具和测试夹具
```

模块可以先由少量文件实现。依赖方向以契约和领域为内核，平台和 SDK 为适配层。核心领域不反向依赖桌面组件或终端库。

### 18.2 一种 TypeScript 参考配置

TypeScript 统一开发语言；受支持的 Node.js 长期支持版本承载后台；Fastify 承载 HTTP 与结构校验；SQLite 负责本地持久化；Electron/React 与 Commander/Ink 提供双端；Agent SDK 经 RuntimeDriver 接入。

Fastify 提供基于结构定义的校验和序列化，输入结构应由可信代码管理。[S24](references.md#s24) Node.js 异步输入输出适合等待模型及工具，持续同步计算应迁出关键事件循环或分批处理。[S18](references.md#s18)

项目在技术验证阶段记录准确版本及锁文件，逐一验证原生依赖、打包和目标平台。参考配置不把某个版本号升级为公共 Harness 契约。

## 19. 观测、性能、数据治理与发布

### 19.1 统一关联标识

日志和诊断记录关联命令、会话、分支、任务、尝试、模型调用、工具执行与构建版本。OpenTelemetry 的 Trace（调用追踪）和 Span（追踪片段）可帮助关联跨模块执行，但诊断追踪不能替代权威业务记录。[S26](references.md#s26)

敏感输入输出默认脱敏或按权限保存。事件流、指标、日志、审计和产物使用各自的保留策略，删除时处理引用、导出和备份边界。

### 19.2 指标从用户行为定义

受理延迟统计到持久化回执；展示延迟统计到客户端应用已提交批次；停止分别测请求受理、取消传播和实际清理。模型生成时间与本机界面响应分开统计。

性能目标由基准机、并发数、历史规模、日志规模和网络条件共同定义。例如本地参考场景可把受理和事件可见的第 95 百分位各设为 500 毫秒目标，随后实测调整。此数值是工程目标，不是已取得的性能结果。

### 19.3 发布及升级

安装包、CLI、后台和数据库明确版本关系。启动时协商协议，发现不兼容后台时给出升级路径，而不是再启动一个占用相同数据的实例。

升级先处理活动任务和备份，迁移后核对数据与检查点。回滚程序版本只有在数据库及检查点兼容时才成立。原生依赖、代码签名、系统权限、自动更新渠道和离线安装都需要目标平台验证。

Playwright 提供实验性的 Electron 自动化能力，可以用于桌面测试；安装包仍需要真实操作系统中的完整路径验证。[S25](references.md#s25)

## 20. 模块开发顺序：先证明契约，再连接真实依赖

详细阶段任务及完成条件见[开发路线](roadmap.md)。推荐主路径如下：

```text
P0 场景与技术风险验证
  → P1 契约、领域与状态机
  → P2 持久化受理和可查询控制面
  → P3 可控模型与工具的完整执行
  → P4 共享客户端、投影及双端真实接入
  → P5 真实模型、权限及工作区工具
  → P6 恢复、分支和跨端控制
  → P7 安装、升级与发布验收
```

界面外壳、平台能力调查和 SDK 技术试验可以并行；依赖未确认时使用有标记的模拟实现。每个阶段都有一个可观察的闭环，避免以目录或函数存在作为完成依据。

从现有产品迁移时，先映射已有接口和存储，再为一个入口接入适配器及影子查询。只有一个写入所有者；读取对照可以双跑，具有外部副作用的执行不做无约束双写。

## 21. 测试与验收：让每条承诺对应证据

### 21.1 三种测试边界

规范化事件替身检验执行和状态；原始提供方响应夹具检验适配器；真实模型和工具集成检验环境连接及副作用。三者分别标记，不能相互代替。

测试模型质量时关注任务结果；测试 Harness 正确性时关注固定输入下的执行轨迹、状态与权限。可控失败、延迟和重复事件有助于精确复现异常。

### 21.2 最小验收集合

应覆盖直接完成、工具闭环、同命令重复、冲突命令、两个客户端同步、审批竞争、长同步等待、等待者断开、停止与完成竞争、检查点恢复、未知副作用、历史分支、游标过期、慢客户端、未授权访问和安装升级。

每项关联接口、领域不变量、测试环境及证据位置。具体矩阵提供在路线附录中，项目按实际测试填写通过、失败或未验证。

### 21.3 五类证据

| 证据 | 支持的判断 |
| --- | --- |
| 接口与契约测试 | 请求、回执、错误及版本符合约定 |
| 执行轨迹 | 模型、工具、任务具有正确因果关系 |
| 存储回读 | 状态、内容和结果真实提交 |
| 外部状态检查 | 文件、进程及远程资源实际变化 |
| 双端用户路径 | 用户能够从入口完成预期操作 |

文档校核、静态类型检查、模拟测试、真实集成和生产部署分别报告。证据范围就是交付结论的边界。

## 22. 将指南变成项目的开发基线

采用本指南时，先确认目标用户路径、部署配置、首个验收平台、工具权限模式和恢复范围。随后将公共契约落实为机器可验证结构，记录真实 SDK 与平台的适配差距，再按模块顺序推进。

一份可交给工程师的简短指令可以是：

> 以通用 Harness API 为产品边界，实现会话、发送、查询、同步等待、事件订阅、停止、继续、审批、分支和产物访问。保持稳定身份、单一权威记录及可恢复同步，通过执行驱动复用现有 SDK。先用可控模型和工具证明契约，再接入真实工作区与双端。按阶段提供接口、存储、外部效果和用户路径证据，明确平台与恢复能力范围。

每轮变更补充目标、当前基线、必须保持的语义、实施范围和验收差异。复杂知识进入可引用的契约与决策记录，使后续语言能够简短而准确。

**完整 Agent 产品的工程基础，是一套能被不同入口一致调用、能解释实际执行、能处理控制与故障、并能由证据验证的 Harness API。**
