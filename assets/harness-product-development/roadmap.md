## 1. 以可验证交付组织推进

本路线围绕通用 Harness API（Agent 执行控制接口）安排依赖。每个阶段给出输入、实施模块、用户可观察的结果和进入下一阶段的条件。

路线是实施规划，不表示任何具体仓库已经完成这些阶段。项目应记录提交版本、实际环境、模拟范围、测试证据和未验证项目。允许并行开发，但阶段门槛以依赖契约和真实集成为准。

最小推进单位是 Vertical Slice（纵向功能切片）：从一个实际入口经过必要的后端、执行、存储和展示，得到可观察结果。目录和接口声明帮助组织代码，功能切片证明它们能够一起工作。

## 2. 先确定项目配置

启动时写一页项目配置，至少包括：

| 决定 | 需要写明的内容 | 对开发顺序的影响 |
| --- | --- | --- |
| 用户与资源主体 | 单用户、组织或服务账号 | 身份与授权入口 |
| 客户端范围 | 桌面、CLI、Web、业务集成 | 首个端到端入口 |
| 执行部署 | 嵌入式、本地后台、远程服务 | 生命周期、发现与通信 |
| 任务共享 | 是否控制同一个运行中任务 | 共同执行所有者 |
| 工作区位置 | 本机、WSL、服务器或远程工具 | 路径、权限与进程适配 |
| 工具信任等级 | 可信代码、受限工具、强隔离 | 真实工具开放门槛 |
| 恢复范围 | 历史重建、执行继续、文件回滚 | 检查点及外部效果处理 |
| 首个验收环境 | 操作系统、终端、数据库和依赖 | 发布与测试组合 |

本地双端参考配置：单用户、一个后台、一个权威数据库，桌面和 CLI 连接同一执行所有者，先验证一个操作系统，再分别开放其他平台。它是缩小第一轮验证面的选择，公共接口仍保留部署扩展能力。

## 3. 模块依赖图

```text
P0 产品配置 + 高风险接入试验
                 |
P1 公共契约 + 领域对象 + 状态规则 + 权限模型
                 |
P2 持久化命令受理 + 查询 + 幂等 + 执行队列
                 |
P3 可控模型/工具 + 真实控制器 + 事实提交
                 |
P4 快照/订阅 + 共享客户端 + 展示投影
             /                   \
      桌面接入                 CLI 接入
             \                   /
P5 真实模型驱动 + 授权工具 + 工作区执行
                 |
P6 停止/继续 + 故障恢复 + 历史分支
                 |
P7 安装/升级 + 性能/安全 + 发布验收
```

SDK（软件开发工具包）技术验证和平台隔离调查在 P0 开始；其正式适配在契约稳定后接入。桌面外壳可提前搭建，主要执行行为通过 P4 的统一客户端进入。

## 4. P0：产品边界与高风险接入验证

### 输入

项目配置、一个最小用户场景、候选执行框架及目标平台。

### 实施

确认 `send`、`wait`、`stop`、`resume`、审批和历史操作的产品语义。建立术语映射，尤其是业务任务、SDK 运行、模型调用和工具执行的对应关系。

针对候选 SDK 做一个独立试验：固定第一次模型输出工具调用，执行一个可控工具，再返回最终内容。记录实际事件，观察审批暂停、取消、清理、状态序列化和继续行为。验证外部工具是否能够经过产品的授权与结果记录入口。

同时检查目标平台的后台启动、进程清理、凭据保存、原生依赖打包和隔离机制。文件与真实 Shell（命令解释环境）接入前，先明确安全模式及预期威胁。

### 交付与门槛

产出能力映射表、原始事件样本、已观测行为、缺口及处理选项。能够回答“一次 SDK 运行何时只是等待审批”“取消后什么时候清理结束”“检查点能否跨重启使用”。不支持的能力明确标记。

**阶段门槛：**项目确认最小范围和技术风险处理方案，避免将未经验证的 SDK 行为直接写成公共承诺。

## 5. P1：契约、领域与状态机

### 实施模块

`contracts`（请求和事件契约）、`domain`（领域对象与规则）以及可信应用上下文。

将接口附录转为实际项目的 Schema（运行时数据结构约束）、客户端类型和错误定义。确定对象身份、命令幂等范围、分支版本、控制版本和游标范围。

编写状态转换测试：排队、运行、审批等待、停止中、已停止、完成、失败和需要恢复。区分任务状态与尝试最终处理记录。预先定义等待审批不是任务完成、停止结果未知需要核对等规则。

权限模型此时就确定主体、操作、资源和环境。尚未实现的危险工具默认不可执行；后续各阶段不能通过绕过权限换取演示进度。

### 交付与门槛

提供契约文件、状态表、不变量、错误映射及可执行测试。跨进程输入执行运行时验证，TypeScript 类型只承担开发期约束。

**阶段门槛：**同一请求和事件在所有消费者中具有相同业务含义；存在一组可自动检验的合法和非法状态转换。

## 6. P2：持久化受理与控制面骨架

### 实施模块

存储、命令处理、工作区与会话管理、查询、持久执行队列及后台生命周期骨架。

在一次事务中保存任务输入、Turn（任务轮次）、RunAttempt（执行尝试）、命令回执和待执行记录。并发同命令只产生一个有效任务；相同标识不同内容得到冲突。

实现查询和命令回执恢复。模拟响应丢失后，用原 `commandId` 找回相同任务。任务受理后立即杀掉服务进程，再启动后仍能发现待执行工作。

建立一个执行所有者；两个客户端同时启动时连接同一个目标实例。若 P2 尚未接入真正执行，返回排队或明确开发状态，不展示虚假的完成结果。

### 交付与门槛

提供 API（应用接口）请求记录、数据库回读、重启测试及幂等测试。数据库迁移和测试数据隔离从这一阶段建立。

**阶段门槛：**受理回执代表可找回的工作，网络响应丢失或后台重启不会让已受理任务静默消失。

## 7. P3：可控依赖下的完整执行

### 实施模块

任务控制器、执行驱动接口、模拟模型、模拟工具、基础授权、事实记录及结果查询。

使用 Scripted Model（按脚本输出的模拟模型）和 Mock Tool（模拟工具）控制外部不确定性，真实执行任务控制和状态提交。

固定场景：

```text
受理任务
  → 模型调用 1 返回工具意图
  → 工具授权及执行 1
  → 保存结果并进入模型上下文
  → 模型调用 2 返回最终内容
  → 保存 finalContentRef
  → 提交尝试结果
```

同时覆盖直接回答、工具失败后继续、审批等待、取消和预算耗尽。检查下一次模型输入包含匹配的工具调用与结果，调用和工具身份在整条链路中保持一致。

把同步 `send` 实现为受理加等待；让测试时间跨越多段传输等待，证明逻辑等待没有被短网络期限截断。使用可控时钟可以加速时间策略测试，真实取消和进程测试仍需单独执行。

### 交付与门槛

提供预期轨迹与实际轨迹对照、状态回读和结果。明确模拟替换的边界：真实 Harness 控制系统保持在测试路径中。

**阶段门槛：**在不依赖真实模型智能的情况下，可以重复证明完整任务推进、控制和结果关系正确。

## 8. P4：共享同步与双端接入

### 实施模块

快照、事件订阅、游标与去重、共享 HarnessClient（业务客户端）、展示投影、桌面和终端适配。

先完成一个客户端从快照位置继续消费事件，再让第二个客户端在工具运行中接入。测试完整批次应用、半条流断开、重复批次、游标过期和投影滞后。

展示层用同一份权威事实生成相同业务结构，桌面和终端独立实现视觉。工具输入输出、状态、审批和最终回复具有稳定关联。

桌面通过受限预加载接口接入可信主进程，主进程连接后台。CLI 的交互和机器模式使用同一个业务客户端。机器输出、退出码、输入粘贴、中文输入及终端尺寸变化在这一阶段形成契约。

### 并行方式

桌面与 CLI 可以同时开发，但先冻结契约、快照和视图数据样本。跨客户端发现的偏差优先修复公共同步或投影；各端特有的布局问题在端内解决。

### 交付与门槛

桌面发起、CLI 观察，CLI 审批、桌面更新；关闭一个入口后另一个继续，重新进入看到相同已保存状态。此时仍可使用模拟模型与工具，但必须使用真实应用、后台、传输和数据库。

**阶段门槛：**两个入口已真正连接同一个可观察任务系统，而非各自播放演示数据。

## 9. P5：真实执行框架与授权工具

### 实施模块

真实 RuntimeDriver（执行引擎适配器）、模型配置、凭据引用、文件和程序工具、审批强制点、工作区资源调度。

将 P0 中验证的 SDK 或自有执行循环接入 P3 契约。用提供方原始响应夹具测试规范化适配，再运行真实模型集成。提供方未暴露的推理、重试及托管工具细节保持明确边界。

按低风险到高能力接入工具：受限目录与文件读取、文本搜索、按文件版本应用补丁、受控程序执行。每项记录权限、资源范围、输出上限、取消和恢复策略。

对真实 Shell 工具测试子进程、环境变量、网络限制、超时和进程树清理。安全隔离不足时保持已声明的可信本地模式；需要强隔离的场景在对应机制通过验证后开放。

### 交付与门槛

在独立测试工作区完成一项真实检查与修改，核对实际文件差异、工具结果、最终内容和双端显示。测试未经授权的请求被真实阻断。

**阶段门槛：**SDK 事件、模型协议、工具副作用和权限控制已经连接至同一权威事实链。

## 10. P6：恢复、分支与控制竞争

### 实施模块

兼容检查点、恢复协调、执行所有权、状态核对、停止与继续、历史分支和编辑运行。

在精确位置进行 Crash Injection（故障注入）：任务受理后、工具启动前、外部副作用后、结果事务提交中、已提交但尚未发出事件时。观察并记录重启后的决策。

针对结果未知操作，验证不会盲目重复副作用。未确认清理的工作区保留隔离或限制。停止与完成竞争、两个客户端审批竞争、恢复与新输入冲突分别测试。

实现历史编辑的原子分支提交，验证旧上下文和新输入不会重复进入模型。回退预览、取消预览与确认执行使用不同控制语义。工作区回滚作为独立扩展测试。

### 交付与门槛

提供每个故障位置的已提交事实、实际外部状态和恢复结果。检查点能否恢复依实际版本与配置判断，跨版本情况必须有迁移或明确拒绝。

**阶段门槛：**对系统已知、未知和需要人工决定的状态，两个客户端均能准确表达；继续执行具有可核查依据。

## 11. P7：安装、升级与可交付产品

### 实施模块

安装与启动、命令行入口、后台发现、协议协商、数据迁移、诊断导出、性能治理和发布流程。

从一个没有开发环境隐含依赖的用户环境开始：安装、创建工作区、配置模型、发送任务、审批、查看产物、退出、重新接入、升级和卸载。明确卸载是否保留数据以及如何导出。

记录原生模块与应用运行时版本。升级期间处理活动任务、备份和检查点；旧客户端连接新后台时按协议兼容规则处理。数据迁移不能被较旧程序静默降级。

使用长历史、大工具日志、慢消费者和多个等待者进行性能验证。按条件记录百分位延迟、内存上限、停止清理时间和恢复耗时，不把模型服务延迟混入本机交互指标。

### 交付与门槛

提供目标平台安装包、版本清单、安装用户路径、回归结果、运行说明、数据备份和恢复步骤、安全能力及限制。

**阶段门槛：**从安装入口到实际结果，再到停止、重连和升级，均有真实环境证据。公开能力声明与已验证范围一致。

## 12. 横向模块如何穿过各阶段

| 横向能力 | 开始阶段 | 后续深化 |
| --- | --- | --- |
| 身份与权限 | P1 定义，P2 检查请求 | P5 强制工具控制，P7 安全验证 |
| 可观测性 | P2 关联命令与对象 | P3 调用轨迹，P6 故障，P7 运维 |
| 数据保留 | P2 存储范围与版本 | P4 缓存/游标，P6 恢复，P7 迁移删除 |
| 测试 | P1 状态与契约 | 各阶段增加真实边界 |
| 文档与基线 | P0 产品配置 | 每阶段更新当前契约及证据 |

这些能力不是最终上线前统一补加的装饰层。早期先建立正确入口，再随着实际能力扩展。

## 13. 建议固定的十二条不变量

| 编号 | 规则 |
| --- | --- |
| I01 | 受理成功的命令可以用稳定身份找回任务与回执 |
| I02 | 同作用域同命令同内容只产生一次业务受理 |
| I03 | 模型调用、工具意图、实际执行和结果保持正确关联 |
| I04 | 尝试处理结果由权威控制器提交，界面流结束不替代它 |
| I05 | 等待和订阅断开不隐式取消任务 |
| I06 | 工具副作用经过有效授权和受控执行边界 |
| I07 | 审批绑定的内容与实际执行条件一致 |
| I08 | 状态、结果引用和关键事件保持约定提交一致性 |
| I09 | 客户端状态与已应用游标保持一致 |
| I10 | 未知副作用在核对前不会被自动重复执行 |
| I11 | 对话分支变化和工作区回滚具有分别定义的范围 |
| I12 | 过期执行者和冲突任务不能越过当前资源所有权 |

项目可增加业务不变量，但修改已有语义时需要相应接口、迁移和回归决策。

## 14. 验收矩阵

以下是应由项目执行的验收设计，当前状态统一为“待项目执行”。测试描述不代表已经通过。

| 用例 | 场景 | 接口/边界 | 主要断言 | 阶段 |
| --- | --- | --- | --- | --- |
| T01 | 模型直接返回结果 | send → wait | 一个任务关联内容及最终处理结果 | P3 |
| T02 | 模型调用工具后继续 | 驱动 → 工具 → 上下文 | 意图、结果及下一调用正确对应 | P3 |
| T03 | 相同命令并发重试 | 命令受理 | 只创建一个任务与回执 | P2 |
| T04 | 同命令标识不同内容 | 幂等存储 | 返回冲突，不启动新任务 | P2 |
| T05 | 受理后响应丢失 | getCommand | 找回原 task/attempt，保持身份 | P2 |
| T06 | 同步等待跨多段网络时限 | send sync / wait | 续接同一目标，不提前完成 | P3 |
| T07 | 等待审批期间同步调用 | wait | 默认保持等待；显式策略才返回关注状态 | P3 |
| T08 | 等待者取消或断线 | 客户端/控制面 | 只取消观察，后台任务继续 | P3 |
| T09 | 两端同时处理审批 | 审批事务 | 一个有效决定，其他得到原结果或冲突 | P4/P6 |
| T10 | 停止排队任务 | stop | 任务不再启动，回执及结果可查询 | P3 |
| T11 | 停止与自然完成竞争 | 状态机/执行者 | 一个有效终态，已有结果保留 | P6 |
| T12 | 停止后立即继续 | attempt/wait | 旧等待者得到旧结果，新尝试另有身份 | P6 |
| T13 | 旧停止命令晚到新尝试 | stop 目标校验 | 不误停新尝试 | P6 |
| T14 | 客户端在工具运行中加入 | snapshot/subscribe | 从一致位置继续，无缺漏或重复 | P4 |
| T15 | 半条 SSE 消息断开 | 同步读取器 | 不推进未应用游标，重连可恢复 | P4 |
| T16 | 重复批次及内容片段 | 客户端状态 | 工具单元与文本不重复追加 | P4 |
| T17 | 游标过期或过滤范围变化 | 事件接口 | 明确重建要求，不跨范围泄露 | P4 |
| T18 | 投影落后于最新事实 | snapshot | 返回实际投影位置并正确补齐 | P4 |
| T19 | 工具副作用后、结果前崩溃 | 恢复协调 | 核对外部状态，不盲重试 | P6 |
| T20 | 数据库提交失败 | 事务 | 不出现完成状态对应缺失结果 | P2/P6 |
| T21 | 事实已提交、消息未发布 | 发布与补齐 | 重连或发布恢复后可查询完整事实 | P4/P6 |
| T22 | 检查点损坏或版本不兼容 | resume | 拒绝危险恢复并给出明确原因 | P6 |
| T23 | 编辑历史中途请求重试 | editAndRun | 一次分支及任务创建，旧历史保留 | P6 |
| T24 | 取消回退预览 | 客户端/分支 | 不产生新任务或文件修改 | P6 |
| T25 | 不同路径指向同一工作区 | 资源调度 | 同一可写资源按策略协调 | P5/P6 |
| T26 | 审批后请求或脚本变化 | 执行许可 | 重新验证，旧许可不能被替换滥用 | P5 |
| T27 | 未授权工具或路径 | 工具执行边界 | 实际拒绝，无对应副作用 | P5 |
| T28 | 不可信内容诱导越权 | 模型/权限边界 | 执行限制仍生效 | P5 |
| T29 | 两客户端同时启动后台 | 启动器/实例锁 | 连接唯一预期实例 | P2/P7 |
| T30 | CLI 机器模式出现审批 | 输出与退出 | 结构化返回关注状态和任务身份 | P4 |
| T31 | 大输出与慢客户端 | 输出存储/背压 | 有界内存，能够断开并补齐 | P7 |
| T32 | 干净环境安装及升级 | 发布/迁移 | 完整用户路径成立，数据兼容可核对 | P7 |

矩阵编号可直接引用在任务、提交和验收报告中。它们是覆盖入口，复杂产品还需增加权限主体、工具类型和目标平台组合。

## 15. 不同测试替身验证不同层

**模拟规范化模型事件**适合验证状态机和任务推进，但不会证明提供方原始协议解析正确。**原始响应夹具**适合验证模型适配器。**模拟工具**适合固定权限和控制分支，但不会证明操作系统实际隔离。**真实工具测试**证明环境行为，同时需要避免影响用户工作区。

测试应真实穿过被验证层。验证 Harness 时保留真实命令控制、记录与投影，只替换不稳定依赖；验证客户端重连时保留真实传输与服务；验证安装时使用实际安装包。

对性能、取消和跨环境恢复，应记录实际计时与操作系统证据。模型的回答质量通过单独任务评测，不与 Harness 状态正确性混成一个模糊分数。

## 16. 证据包与完成标准

建议每个阶段保存：

```text
evidence/
  environment.json       构建、平台、依赖和配置标识
  scenarios.md           输入、预期、实际结果及模拟范围
  api-results/           请求、回执、错误和结果
  traces/                关联执行轨迹
  persistence/           关键事实回读
  external-effects/      文件、进程或远程资源检查
  client-results/        桌面、终端和机器输出
  limitations.md         已知限制与待验证范围
```

目录是组织示例。敏感数据、令牌和用户文件不应随证据包公开；使用专用测试样本并按策略脱敏。

完成标准包括：行为符合契约、证据覆盖相应路径、代码和测试版本一致、已知限制明确、当前文档已更新。实现存在、测试执行、测试通过和已经部署分别报告。

## 17. 项目推进中的决策记录

每项重要决策记录范围、原因、接口影响、替代方案、验证方式和回退条件。优先记录：执行所有者、停止和继续语义、分支边界、权限模式、同步协议、工作区锁、检查点兼容和数据升级。

无需为每个函数名建立决策文档。判断标准是：变化是否影响用户行为、跨模块契约、安全、存量数据或部署方式。

当原假设被新证据推翻时，先更新契约及测试，再修改实现。已解决的临时讨论保留在历史，当前实施入口引用有效基线。

## 18. 从已有产品迁移

首先列出已有用户路径、公共接口、权威数据和真实执行者。建立旧到新对象映射，保留原始身份或可追溯关系。

可以先为现有后台提供 Harness API 适配层，再逐步切换桌面与 CLI。读取投影可以并行比较，实际写入和工具副作用保持单一控制，避免影子测试重复修改文件或调用外部服务。

存量会话转换需要检查工具结果、最终内容和分支关系。无法恢复执行的旧记录仍可提供历史查看，并在能力上明确区分。

迁移完成的证据包括现有功能回归、新契约测试、存量数据对照和真实双端路径。

## 19. 可直接交付给开发 Agent 的任务骨架

```text

当前基线：
- 产品范围、部署配置和平台：【填写】
- 契约/代码/配置版本：【填写】
- 已有证据及真实缺口：【填写】

实施：
读取当前实现并映射模块责任；复用已有框架能力。
保持【相关不变量编号】，在授权范围内完成最小有效改动。
涉及外部副作用或未确认产品决定时，按项目授权规则处理。

验证：
执行【Txx 用例及项目补充场景】，明确真实与模拟边界。

```

## 20. 推进路线的最终判断

每完成一阶段，应能用 API 演示新的能力，用记录解释实际发生的事，用测试证明关键异常有明确结果，再用客户端验证体验。这样的顺序既允许模块并行开发，也能持续检验它们组合后的产品行为。

**模块开发顺序的依据，是契约、事实和执行边界的依赖；完成顺序的依据，是用户路径和证据。**
